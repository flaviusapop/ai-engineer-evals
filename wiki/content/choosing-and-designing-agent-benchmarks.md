A benchmark is useful only in relation to a question. A difficult public agent task can probe a capability frontier without resembling the work for which a team is buying an agent; a private task can resemble that work without automatically representing it. Before comparing scores, state the decision, the work distribution and the capability the tasks are supposed to exercise. The question of how far findings apply beyond the studied tasks and conditions is **external validity**.

## Start with the decision and the capability thesis

For deployment selection, sample the actual requests, available tools, inputs and constraints. A curated demonstration may prove that a tool connection works while hiding how people use it: in one internal rollout, a pointed demo worked, but teammates' incomplete descriptions led the agent to create workflows that neither party understood. This is an anecdote, not a failure-rate estimate, but it suggests including ambiguous requests and actual users' material in a task set. A post-incident benchmark can instead ask an agent to consult logs, chat and documentation to recover a diagnosis, testing organizational context use as well as code generation. Such private tasks complement public probes; they still require evidence that the cases represent the intended workload. [cite:jJQoVkd5yLg:c02] [cite:q4Tr-DknG2M:c03]

Difficulty and practical value are different judgments. One speaker questioned the economic value of asking an agent to build a C compiler in Rust; another used that task family as a deliberate project-scale stress test. Neither purpose invalidates the other: a frontier capability probe needs headroom, whereas a purchasing decision needs evidence about work the buyer values. A broad coding suite can also be a small slice of possible work even if it contains thousands of tests; optimizing its score alone need not produce general capability. The warning is qualitative, not a universal minimum task count. [cite:jWq-aZIU0kM:c09] [cite:Rx8f05JI_WA:c01] [cite:A48uhxfxbsM:c09]

A research benchmark can make its own **capability thesis** explicit. For example, terminal-oriented tasks express a speaker's bet that command-line interaction is a useful general agent interface. That thesis guides the task choice; it does not establish that the benchmark caused adoption or broader research progress. At a more specific level, a training speedrun fixes data and target validation loss while minimizing time; an optimizer-only track narrows which changes are allowed. The two tracks test different scopes of improvement, and achieving the same loss is not proof of equal general model capability. [cite:iNkFlCiij0U:c05] [cite:oVsEddfhdxc:c01]

Artifact utility is a third, separate question. The designer of ParallelKernelBench describes selecting real inference operations lacking good kernels, so specialized solutions could become useful artifacts. That is an intended utility criterion, not a reported deployment gain, evidence of generalization, or proof that the evaluator cannot be gamed. Check both whether the artifact works for the operational need and whether the score means what it claims. [cite:AVMr9PMINyo:c02] [cite:AVMr9PMINyo:c09]

## Choose the environment, horizon and output

Specify three independent design axes: **environment realism**, **autonomy horizon**, and **output complexity**. A realistic environment need not demand sustained autonomous work; a long task need not produce a complex artifact. This is a proposed framework, not a validated universal taxonomy. [cite:TyPpSRXGhbc:c12]

For example, compare a short, structured financial question with a multi-experiment scientific decision that must interpret results against prior literature, experimental design and the original goal. The latter can resemble an industry go/no-go decision more closely, but is harder to construct and verify. The described examples simulate scientific decisions, not successful autonomous drug discovery. Likewise, concatenating independent subtasks creates a longer episode without necessarily testing the state dependence that makes a long investigation difficult: a bad early log query can constrain the downstream diagnosis. Describe both the resources consumed and the dependencies, rather than equating duration with competence. [cite:3ZMUiFaQ3qg:c09] [cite:2aS7aKoXn64:c03]

Security benchmarks need an especially explicit access model. One access-control task family gives an agent basic execution tools against live, chained applications, without source code or internet access. The agent must infer behavior and track state changes across interactions. This is different from discovering vulnerable code in a repository, and a score applies to that environment and access surface—not cybersecurity as a whole. [cite:O-CBZ3JtRvo:c03] [cite:O-CBZ3JtRvo:c07]

## Keep challenge while admitting valid tasks

A benchmark needs room to distinguish systems, but a low score alone is not proof of meaningful challenge. A speaker reports that frontier models often score below half on a multi-domain data-science suite; that suggests headroom on that suite, not coverage of every real data-science workflow. Conversely, an apparent plateau can be caused partly by unsolvable or defective remaining items, which may also bias rankings. Inspect the failures before announcing saturation. [cite:mMNkdYnIVC4:c09] [cite:-npY6XjM8CQ:c09]

When valid tasks genuinely stop distinguishing systems, add or update meaningful challenges; revisit the evaluation when the agent's harness changes too. Keep stable regression cases alongside new tasks so earlier requirements remain testable. Balance difficulty against completion time: an exam too easy loses signal, while one too difficult or long may not be finished. One speaker describes moving from vending machines to a cafe as models improved, but this progression is anecdotal, not a validated upgrade threshold; adaptive evaluation for changing harnesses is a proposal. [cite:cO8qC6HBuBg:c12] [cite:4VhbYlfC7Gs:c02] [cite:Ubwb6NzegyA:c07]

Admit a task only after checking that it is achievable, nontrivial, functionally correct and supported by a reliable environment. Examine pass rate alongside tool calls, output length and failure categories: a lengthy trace or low pass rate might reflect hard reasoning, an ambiguous instruction or a broken setup. Separate incomplete reasoning from environment failures. One reported accepted-task comparison used these indicators together, but did not publish enough task counts or distributions to make any one threshold a general rule. For the details of packaging and auditing an individual task, see [[specify-and-audit-meaningful-benchmark-tasks]]. [cite:YYH0DMQr30A:c01] [cite:YYH0DMQr30A:c03] [cite:YYH0DMQr30A:c04]

## Distinguish novelty and verifiability from score

Research-record improvement is not necessarily novel discovery. In preliminary speedrun experiments, agents could access human records; one restarted agent incorporated new human work and improved on it. The speaker assessed observed solutions as recombinations or incremental improvements rather than genuinely new optimizer mechanisms. A useful record can therefore coexist with an unmet novelty objective. If independent discovery matters, define that criterion separately; proposed no-access, papers-only and full-access conditions would distinguish what agents can use, but were not yet a completed controlled benchmark. Novelty judgments still need scrutiny. [cite:oVsEddfhdxc:c05] [cite:oVsEddfhdxc:c06]

One research arena offers a different objective: agents select problems, discuss approaches, submit solutions for automatic scoring and inspect or download one another's submissions. Where solutions can be verified and shared, this design permits cumulative work alongside competition, but it does not demonstrate a collaborative benefit. Document access to shared submissions when interpreting results: building on others' work is not evidence of independent discovery. [cite:mMNkdYnIVC4:c03] [cite:oVsEddfhdxc:c05]

Deterministic checks can give clear feedback for open-ended search when the target has a well-defined verifier, but selecting only such tasks excludes important work. In changing web environments a fixed check may be brittle or reject a valid alternative; an ungrounded model judge can also misjudge. Verifiable tasks and messy iterative work should be connected by measured transfer, not assumed equivalent. Audit the verifier and its resistance to shortcutting separately; see [[scoring-outcomes-and-diagnosing-behavior]] and [[protect-benchmark-integrity]]. [cite:mMNkdYnIVC4:c02] [cite:xLxhT2ZI7UM:c01] [cite:YYH0DMQr30A:c09]
