A production trace is evidence of what happened, not yet a test of what should happen. A useful offline case needs a reconstructable situation, an expected outcome or observation, and a way to assess a new run. Keeping that distinction lets a team learn from real work without mistaking a collection of memorable incidents for a representative sample of all users.

## Promote reviewed failures and reliable capabilities

Start with an investigated interaction, correction or complaint. A user’s correction is a lead, not necessarily an accurate label of the underlying error; review the context and decide what behavior is actually expected. Record the input, relevant state and tool responses, expected outcome or observation, and a category and owner. A clinical workflow, for example, describes turning expert trace annotations into typed cases with conversation input, expected observation and category metadata. That is a reported workflow, not a clinical-outcome study. [cite:TeErpYBUIeM:c06] [cite:O72p-rBb2bA:c07]

Make the case runnable, reproduce the baseline behavior where possible, and run the candidate on the same case. Compare its output with the original and rerun earlier cases: fixing a single failure can break something that previously worked. A workshop proposes replaying failures through a development endpoint with the production rubric, but its verification path was described rather than fully executed. Scorer quality still matters; reuse of a rubric alone does not validate it. [cite:fnuNVFgLjHA:c10] [cite:2IxD9OB3XuQ:c08] For investigation and scorer design, see [[tracing-failure-analysis-and-evaluator-methods]] and [[validate-judges-against-human-labels]].

A capability case may initially be an ambitious target; once it passes reliably enough for its intended use, keep it as a regression check. Decide whether the behavior merits a hard per-case requirement or a noisy aggregate target. In one teaching example, every financial report must name its ticker, while actionability is assessed as an average. A finite perfect run does not prove a true 100% success probability, and passing the suite says nothing conclusive about untested behaviors. [cite:SHMCGrNJJGc:c15]

A growing suite preserves history but consumes time and money. Categorize cases so a relevant subset can run during iteration and a broader suite at integration; the suggested tradeoff gains faster feedback at the cost of potentially later detection. It is a proposed workflow, not a measured missed-regression rate. Owners should review redundant cases rather than blindly retaining every trace, while retaining consequential distinct failure modes. Release thresholds and promotion decisions belong to [[production-governance-and-release]]. [cite:ObTPqBGsEbA:c10] [cite:ObTPqBGsEbA:c13]

## Refresh from real use, not just failures

Collect eligible inputs, outputs, intermediate steps, outcomes and feedback from production—or user acceptance testing when production evidence is unavailable. Select both successful and unsuccessful interactions, have knowledgeable reviewers label expected behavior, and retain provenance and selection rationale. Successes protect useful behavior that a failure-only library would miss. Usage changes can make an old suite less relevant even when the model has not changed. [cite:FB-MLPhL9Ms:c07] [cite:XyV6bSMyq-I:c07] [cite:UGjk3Uk0MxM:c09]

Permission, privacy, retention and missing outcomes must be resolved before keeping an interaction. One reported benchmark effort used opt-in coding records and compensated contributors, then manually cleaned tasks; it did not publish a complete consent protocol or demonstrate representativeness. Production origin alone does not establish either. Sampled and incident-selected cases answer different questions: use [[design-evaluation-distributions-for-decisions]] when estimating performance on a population, and reserve appropriately protected tests for evaluation rather than repeated tuning. [cite:QuuIywMG4s8:c04] [cite:xyL2Ltkh-SA:c08]

Recheck automated judgments against newly reviewed human examples as the suite evolves; a disagreement might expose a bad application response, a bad evaluator, or an ambiguous standard. The suggested ongoing alignment check is not a demonstrated alignment trend or a prescribed refresh cadence. Online monitoring and offline experimentation are complementary; neither term inherently means batch or non-batch. [cite:NKwIX3CiRgU:c09] See [[production-evaluation-and-monitoring]] for ongoing traffic monitoring.

## Freeze comparisons while maintaining living fixtures

Maintain two explicit views: a versioned frozen set for comparing candidates on the same historical circumstances, and a living set for new usage and failure modes. Pin a code commit, injected change and expected result, or record downstream tool responses and replay them while the agent generates a fresh answer. Otherwise a changed environment and a changed agent are entangled. Recorded responses stabilize inputs, not stochastic reasoning; a frozen snapshot also becomes less current over time. [cite:KhRjivBSwiw:c16] [cite:0RNNfxpdbQk:c03]

Realistic fixtures may be large because removing details can remove the trigger. Do not assume a shortened case is equivalent: rerun it against the known behavior before replacing the original. Incident.io reports an alternative to loading an entire large YAML suite: structured operations to list, add, edit or replace individual cases, with instructions for agents using the interface. This is a company workflow report, not a controlled comparison. [cite:L2r6vLlLgs8:c01] [cite:L2r6vLlLgs8:c02]

## Reconstruct historical work

Completed work offers another source of local tasks. In one case study, roughly twenty merged fix pull requests from one repository supplied parent commits with bugs still present; a model generated task descriptions from the fixing diffs. A candidate agent then worked against the buggy repository. That selection rule is narrow, and the account does not establish checks against solution leakage or representativeness. [cite:T3SS931wU0I:c06]

When adapting the pattern, preserve the pre-work state, provide only information legitimately available to the agent, and decide what constitutes an acceptable result rather than assuming the historical patch is the only correct answer. Check privacy and selection bias. Archived incidents or support tickets can also generate probes for whether a knowledge base contains the information needed to do actual work; the cited scanner was a preset demonstration, not proof of enterprise-scale accuracy. [cite:rWtbOgl5FTU:c10] [cite:_QAVExf_1uw:c03]

## Use shared baselines, and budget for local maintenance

A reviewed external set is a useful common starting point, not a substitute for local expert review and observed cases. One clinical team announced 200 input and 100 output guardrail scenarios, but the material was not independently inspected and does not establish clinical outcomes or coverage. Adapt and extend such a baseline for the product’s users, policies and actual failures. [cite:O72p-rBb2bA:c10]

Budget for expert task design, labeling, review, replay infrastructure and eventual replacement as well as execution. A speaker’s example of expensive benchmark construction uses hypothetical labor and cost assumptions, not a measured accounting; its lesson is to account for the quality-control and refresh work that cheap case generation can leave out. [cite:-npY6XjM8CQ:c02] For broader coverage decisions, continue with [[building-and-maintaining-evaluation-coverage]].
