An agent can improve because its instructions became clearer, its execution environment changed, or it was given more opportunities to try—not necessarily because the underlying model changed. Optimize the system against the actual task, keeping a simple baseline and a separate evaluation for changes that may make it worse.

## Choose retention and compaction for the actual constraint

First identify what binds: context capacity, latency, cost, or the ability to recall a detail. Retaining history may be the simplest useful baseline. If a few tool outputs dominate the window, try truncating outliers with the omission clearly marked, clearing expendable results, or retaining a recent-turn window before adding a model-generated summary. Selective summaries can preserve decisions while losing details needed later; clearing material can also force expensive retrieval again. Compare downstream task success and total cost, including re-retrieval, rather than treating a shorter context as automatically better. [cite:WP3hjUXd918:c02] [cite:WP3hjUXd918:c18]

In one workshop, cached full history won the initial comparison, which involved only one or two trials. Its speakers nevertheless described an operational compaction cutoff without reconciling it with those longer-history findings. Another team used downstream behavior because it lacked a principled intrinsic measure of context quality; passing those evaluations supports only the tested heuristic. Details on cache economics belong in [[context-and-retrieval]], and loading tool details on demand in [[tool-interfaces]]. [cite:WP3hjUXd918:c18] [cite:esY99nYXxR4:c09]

## Make instructions a testable task specification

State the outcome, relevant authoritative reference, input interpretation, and conditional procedures needed for this task. Start with a minimal version and add observed local gotchas instead of copying a complete manual into every run. A rule should say when it applies: a workaround for one framework location may be harmful elsewhere. Compare the same task with and without guidance; an instruction can be well written and still distract the model. One practitioner reported 77% correctness with a skill and 97% without it, but supplied no trial count or uncertainty, so this is a reason to test, not a general estimate of skill harm. [cite:JT3OzDKrucU:c08] [cite:vy7o1g2iHY8:c06] [cite:vy7o1g2iHY8:c05]

Minimal does not mean never giving rich examples. In voice-sensitive writing, positive samples and concrete counterexamples can communicate a target that a short instruction misses. The guidance is experiential, without a controlled prompt-length ablation. Evaluate added context against the smaller baseline on the actual writing task. [cite:_dTF3NpPzGo:c11]

## Search prompts with diagnostic feedback

Fix the task contract and scoring checks, then propose instructions, run representative cases, inspect failures, and revise. Reflection can use intermediate outputs, tool responses and errors rather than only a scalar score; that extra diagnostic information matters when rollouts are costly. A prompt found this way can encode the component's role and task-specific constraints, not just a collection of magic phrases. For example, one reported search learned to avoid a library header incompatible with its target hardware generation; the baseline improvement ratio was caption-ambiguous. [cite:OA-Mc60Rboo:c02] [cite:OA-Mc60Rboo:c03] [cite:OA-Mc60Rboo:c05]

A search that keeps only the aggregate leader may discard a candidate that handles a rare case particularly well. Retaining candidates that win on individual examples preserves alternative strengths for further edits or combinations. This Pareto-style frontier is search diversity, not a guarantee of global optimality or unseen performance. In one classification experiment the speaker reported improvement from 68% to about 83% during iteration and 80.2% on an untouched test set; labels were author-selected and sometimes subjective. Those are different estimands, not interchangeable accuracy claims. [cite:OA-Mc60Rboo:c04] [cite:A48uhxfxbsM:c01] [cite:eAXxdtNlK04:c03] [cite:eAXxdtNlK04:c04]

For mechanically checkable requirements, a program specification can generate candidates and test constraints directly: a demonstration searched for numbered lines with specified word counts and initials. It did not report held-out performance. Keep a final test independent of repeated selection and inspect failures of the checks themselves; a score is only as meaningful as the specification. [cite:UGjk3Uk0MxM:c15]

## Compress and adapt without changing the contract

Instruction compression is not model-weight compression or conversation-history compaction. Hold input, output schema and task requirements fixed while searching for fewer instruction tokens, then separately test correctness and cost. A fictional classifier example reported a 51% reduction in instruction tokens, not proof of production savings or preserved quality. Historical production answers can seed training labels, but they may be inconsistent or wrong: review disagreements so a genuinely better answer is not rejected merely for differing from the old system. Reoptimizing for a smaller model is distinct from copying the larger model's prompt; downsizing trials can still overfit or fail the release gate. [cite:8g1N_a3h9H0:c05] [cite:8g1N_a3h9H0:c07]

Whole-prompt rewriting can discover useful details but accumulate instructions. Selecting a bounded subset of prepared components would cap growth while limiting what the search can express; that approach was proposed, not experimentally established as optimal. Similarly, model-specific corrections may help one family and overcorrect another. Ablate skills, compile only applicable rules, and retest scaffolding after a model upgrade; remove workarounds only when the new combination passes the relevant tasks. A speaker's argument that stronger instruction following can make precise prompts more valuable is a hypothesis, not a scaling law. [cite:A48uhxfxbsM:c05] [cite:SQMCtZX3trg:c11] [cite:mR-WAvEPRwE:c11] [cite:OA-Mc60Rboo:c12]

## Search the harness and allocate the budget

When prompt changes plateau, the editable artifact may be control flow, tool availability, state handling, or which role does what. A reported experiment changed a short model-call program into a process involving rule induction, code synthesis, execution, tracing and debugging. This shows an explored search surface, not proof that any scorable program can be optimized reliably. Before adding architecture, test whether supplying domain context and explaining available tools solves the problem; that priority is practitioner guidance rather than a controlled comparison. [cite:OA-Mc60Rboo:c06] [cite:OA-Mc60Rboo:c08] [cite:hd7TOvmyAxU:c09]

At a fixed inference budget, compare an execution-only system with alternatives that reserve some compute for an adviser, a grader, or coordination. An adviser can be consulted mid-task; a grader can request revision; a later reflection can help future runs. A strategy that spends more tokens is not evidence that its orchestration is intrinsically better. Composing these roles is an architectural proposal, and results from particular financial tasks should not be generalized to every workflow. [cite:PXj0p_mW9nI:c01] [cite:PXj0p_mW9nI:c02] [cite:PXj0p_mW9nI:c09]

## Bound repair and make room for divergence

Feed validator errors or critic feedback back to the agent, but limit attempts and inspect the final result. In a query demonstration, a prohibited regular expression was repaired into an allowed exact-title match that found nothing; adding full-text search addressed the information need. Validity and usefulness were separate outcomes, and this was a staged demonstration, not a recovery-rate estimate. If repeated revisions remain below the target, permit a restart rather than preserving a failing approach indefinitely. For voice writing, one practitioner warns that too many critique cycles can make the draft generic; that limit is experiential rather than measured. [cite:ORVh4GivEU0:c09] [cite:ORVh4GivEU0:c10] [cite:mR-WAvEPRwE:c06] [cite:_dTF3NpPzGo:c12]

Creative work has a different objective from passing a syntactic check. Banning a familiar style may merely elicit the next familiar default. External inspiration, a sampled starting color, or fresh-context ranking can introduce diversity; assess whether the result fits the brief, not whether it is merely different. These examples are qualitative, not measured guarantees of originality. [cite:SQMCtZX3trg:c01] [cite:SQMCtZX3trg:c03] [cite:sDMGWK4wZ_w:c06]

## Carry verified lessons into future runs

A within-run critique changes the current attempt. Cross-run learning instead distills a success or failure into scoped guidance that a later run can retrieve or use as a revised procedure; neither changes model weights. For example, a retrospective might notice repeated identical tool calls and store a framework-specific lesson where it applies, rather than burdening every task with it. Replay the triggering case and regression cases before promoting the lesson, and check that future agents actually use it. The cited memory systems report no longitudinal proof that accumulated lessons improve outcomes; automatic pruning remains future work in one example. Runtime retrieval and slower consolidation into persistent guidance can coexist rather than being mutually exclusive. [cite:PXj0p_mW9nI:c04] [cite:vy7o1g2iHY8:c09] [cite:2IxD9OB3XuQ:c07] [cite:Jx4ZFEAq6bY:c05]

For the broader improvement loop, see [[evaluation-driven-improvement]].
