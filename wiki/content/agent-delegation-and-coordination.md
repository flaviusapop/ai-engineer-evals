Splitting work across agents is useful only when the resulting pieces can be coordinated and their results put back together. Begin with the work, not a desired agent count: identify which parts are checkable, what depends on what, and who has capacity to inspect the combined result.

## Select checkable nodes and retain takeover

A whole workflow need not have one autonomy setting. Screen each proposed node: is its output bounded, traceable and checkable against the relevant rules? Can an accountable person inspect the result, stop the run and take over when it fails? An agent might assemble evidence for a lending decision while the difficult, policy-sensitive final decision remains human-driven. These are qualitative screening questions, not an authorization score. [cite:_4Ph2dhmUFI:c08]

A proposed stop-and-resume hook returns control to a person when an evaluator detects a condition, accepts a message and continues. Start with close expert review; only reduce routine review when task-specific evidence meets an explicitly chosen policy, while keeping a way to investigate and intervene. The cited staged approach does not specify thresholds or sampling rates. An agent's explanation can aid inspection but can itself be wrong. [[risk-based-safety-and-staged-autonomy|Risk-based autonomy]] and [[agent-authority-isolation-and-runtime-controls|runtime enforcement]] address distinct decisions. [cite:mR-WAvEPRwE:c18] [cite:_4Ph2dhmUFI:c09] [cite:jJQoVkd5yLg:c07]

## Start with a reliable loop; split only for a real boundary

First make one agent loop work on the task. Add a role when it has a distinct job, context, tool set or organizational owner that warrants a handoff. In one diagnostic case, a single prompt had to handle troubleshooting, formatting and failure patterns; improving instructions for one behavior reportedly hurt another. The team separated focused prompts and tool subsets, making roles easier to maintain and test. This is a case observation, not a controlled demonstration that specialists always outperform a single agent. [cite:32nrHU6zHU8:c09] [cite:0RNNfxpdbQk:c01] [cite:0RNNfxpdbQk:c08]

A stage boundary makes it easier to locate a failure, but sequential calls add latency and another place to fail. The same diagnostic team found its trial of a more rigid workflow brittle for open-ended troubleshooting; that experience does not rule out deterministic sequencing when the task requires it. Top-level ownership can remain serial while a worker runs bounded research tasks in parallel. A vendor describes such a design, but does not establish that its fresh-context handoffs improve performance in a controlled comparison. [cite:ZdheJTfLu-s:c05] [cite:0RNNfxpdbQk:c10] [cite:vGCJ7diEtrw:c05]

## Choose topology by dependency and reconcile the whole task

A central orchestrator can distribute dependent work, retain a common view and provide an investigation point. Event choreography lets consumers respond to relevant events without a central round trip, which is attractive when their tasks do not depend on one another. Direct messages can avoid central coordination but fragment state: each participant may see a different version of the task. These are architectural tradeoffs, not measured universal latency or reliability results. Independence here means no execution dependency; it does **not** imply statistically independent model errors. [cite:ObTPqBGsEbA:c07] [cite:ow1we5PzK-o:c02]

A model-selected topology permits adaptation to the problem; a provider favors it, but supplies no comparison protocol. Conversely, a team supporting many integrations used reference patterns to limit variation. A middle choice gives agents discretion over decomposition while retaining explicit bookkeeping and checks for unresolved work. Compare these choices on the actual task and support burden, not on a presumed winner. [cite:qJtcEDc_WJU:c05] [cite:juoNbJiZUi0:c04] [cite:ow1we5PzK-o:c09]

Send each specialist the goal, relevant shared constraints and the context needed for its assignment; configuration inheritance is not necessarily conversation inheritance. One described subagent inherited prompts and tool schemas but not the parent transcript. Preserve shared state and return a structured account of completed and unfinished work, evidence and issues, so the coordinator can identify gaps; see [[agent-task-flow-and-action-evidence|task handoffs]] for action evidence. [cite:FGftGOzfohc:c04] [cite:ow1we5PzK-o:c06]

For example, independently reasonable flight and hotel choices may refer to incompatible destinations. Reconciliation must compare outputs against the **whole** objective and constraints, not merely concatenate them. A judge can flag inconsistency, but it is not proof that every cross-cutting architectural or security tradeoff was considered; a reviewer may still need to challenge missing context. [cite:EcqMYoIV57A:c05] [cite:EcqMYoIV57A:c08]

## Gate specialist participation and investigate competing hypotheses

A narrow specialist need not write a full response every time. In a reported clinical architecture, specialists first decide whether their area is relevant; those with nothing to contribute short-circuit, while relevant outputs go to the main conversation model. This can avoid needless contributions, but the gate can miss a relevant issue. The vendor account does not establish reliability or a measured latency benefit; specialist participation is not approval or independent proof. [cite:AN65uc645mE:c07]

Diagnosis calls for a different pattern. In a reported job-troubleshooting system, triage examines the lifecycle, proposes competing failure hypotheses and sends each to parallel evidence researchers. A supervisor selects a confidence-scored explanation; a separate healer retrieves possible remedies from runbooks, and a report is assembled. This preserves the distinction between evidence for a cause and guidance for responding to it. The scores were not shown calibrated: the highest score is not proof of causality, and a plausible runbook remedy does not prove the diagnosis. [cite:0RNNfxpdbQk:c09]

## Budget the human and validation bottleneck

More parallel agents create more routing, review and integration decisions for people. Measure ready-to-submit delay and retries, CI and review queues, integration and rework, alongside product quality and human interventions. A green check or high PR count is not itself delivered quality. Fix flaky tests and consider incremental builds, caching or sharding where CI is the constraint; preserve time for people to interpret monitoring signals as well as review changes. [cite:dSg0pu8d6qg:c09] [cite:7b9tov5Uc5s:c04] [cite:n97BCfyFIvw:c09] [cite:YXEqC05WEI0:c12]

Backpressure ties generation to available review. In one workflow, a scheduled loop checks for an existing labeled PR before starting and stops if one remains open. That limits outstanding work **per labeled loop**, not across the team. The same practitioner suggests bounded batches or distributing separate PRs among reviewers when capacity allows; reviewer fan-out requires a deliberate change to the one-open-PR rule. Larger PRs may amortize CI waits but make careful review harder. Prioritize a few evidence-rich findings rather than flooding reviewers, and measure whether review and quality actually keep up. [cite:xIt_mTQp6mY:c11] [cite:xIt_mTQp6mY:c12] [cite:dSg0pu8d6qg:c07] [cite:JJGbw4ggaFs:c10]

## Separate coordination planes and check the environment

An execution plane performs the user's work. One proposed evaluation control plane instead collects telemetry, runs simulations and coordinates human review; the talk does not specify its intervention mechanisms. A different vendor architecture uses a PR-validation control plane to coordinate workflow state, alongside an agent runtime and model routing. These planes have different jobs: neither label proves a safety guarantee or quality gain. For monitoring and ownership, see [[production-evaluation-and-monitoring]] and [[evaluation-platform-and-team-ownership]]. [cite:vljxQZfJ9wY:c13] [cite:uuwDWRbxoYo:c08]

Before porting a design, test the actual harness for subagent support, permissions, user interaction, hooks and wakeup on task completion. Identical instruction files do not ensure identical execution. An experimental browser-feedback bridge used a poller that completed after a user annotation, allowing the agent to consume the event; the speaker noted remaining problems and preferred a first-party integration. Report unsupported or degraded behavior rather than assuming the bridge works everywhere. These capability descriptions were made at talk time, not guarantees about current products. [[agent-sessions-and-long-running-work|Session lifecycle]] and runtime authorization remain separate concerns. [cite:SQMCtZX3trg:c09] [cite:SQMCtZX3trg:c10]
