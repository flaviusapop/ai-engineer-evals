An agent does not remember a fact merely because it mentioned it. Reliable reuse requires a place where the fact is owned, a way to find it again, and a reason to trust it for the next task. That place might be a project record, a source document, a worklog, or a curated memory store. The material in the current prompt is only the working view of that larger body of knowledge.

The design challenge is to carry forward enough context to avoid repeated discovery without turning yesterday’s guesses into today’s unquestioned instructions. Knowledge continuity is also distinct from resuming an execution or retaining authority: see [[agent-sessions-and-long-running-work]] and [[agent-authority-isolation-and-runtime-controls]].

## Make project knowledge recoverable

For each fact a later task may need, name its system of record and the path by which a person or agent can recover it. A friendly acknowledgement is not proof that the fact was stored. Record a finding in the issue system, a code decision in the project’s maintained documentation, or a task-specific lesson in a memory store linked to the investigation. A recurring diagnostic agent can then revisit earlier weak signals as evidence accumulates instead of treating every run as a clean slate. This supports continuity, not an automatic guarantee that the old conclusion remains correct. [cite:BInpv7lGp1o:c01] [cite:ImnZ7s68jw8:c04]

A shared code index and project memory can give different coding tools a common retrieval layer; one reported implementation indexes locally, but that does not establish that downstream model requests stay local. Starting a fresh session can encourage useful decisions to be written somewhere discoverable, but it is a practitioner’s preference, not a rule: continuing a session may be more convenient, especially with larger contexts and better retrieval. [cite:dRmWYHuIJxM:c08] [cite:2TLXsxkz0zI:c11]

Preserve reasons as well as outcomes. A decision record should say what was chosen, why, and how the rule is meant to be enforced, with references to relevant evidence or checks. A worklog adds the changing situation: the plan, attempts, evaluations, fixes, results, and surprises. The plan alone cannot tell a successor what actually happened. One practitioner reports that a fresh session resumed a presentation from a worklog; another describes timestamped breadcrumbs for later agents. These are handoff practices, not measured guarantees of continuity. Documentation does not itself enforce a rule; link it to actual checks where appropriate. [cite:504PvfXou5Y:c01] [cite:6MudaeKdBSk:c02] [cite:mR-WAvEPRwE:c13]

Important decisions that remain discoverable can also help after compaction. One speaker reports tolerating repeated compactions because decisions could be looked up again, but that personal experience does not establish lossless retrieval or a safe universal compaction policy. Indefinitely appending everything is not a maintenance strategy either: longer-lived memory may need revision and compression, an area for which the proposed lifetime-scale architectures remain unsettled. [cite:504PvfXou5Y:c10] [cite:CvRngaQZQ3Y:c12]

## Retrieve the right shape of evidence

Different questions call for different retrieval operations. An overview search can show the landscape; detailed semantic retrieval exposes the content of a few promising matches; metadata filters restrict a search to an appropriate time, project, or category; exact matching finds a known identifier or phrase. One harness reports overview summaries of up to 50 chunks and full semantic content for its top 10, plus filtering and grep. Those numbers describe that harness, not optimal defaults. The decision is about the information shape needed for the task, not a universal preference for semantic search. [cite:1IdzkRVmWAA:c03]

Task relevance also matters within memory. A refund workflow may need the procedural lesson to check settlement before refunding, not an unrelated interface preference. That example illustrates a policy rationale rather than a measured financial deployment. [cite:Jx4ZFEAq6bY:c03]

### Build grounded, inspectable context

Where structure can be computed, derive it before asking a model to interpret it. For data transformations, parse the implementation to identify lineage and grain, then profile actual data to check properties such as key uniqueness. SQL parsing alone cannot prove that real join keys are unique. Only after those steps ask narrow semantic questions—for example, classify one column using its type, comments, and local context—and retain the output for inspection and correction. A grounded summary can still be wrong. [cite:KhRjivBSwiw:c02] [cite:KhRjivBSwiw:c17]

A context graph is one way to persist typed assets and relationships with their supporting evidence, so an agent can fetch a relevant dependency subgraph rather than reconstructing an entire system. It can connect catalog facts and warehouse profiles to transformation models; it does not replace the catalog. Update relationships as their sources change. The workshop’s educational graph is not the production implementation, and its broader cross-system workflow was an incomplete vision. A graph is an option, not a prerequisite for all useful project memory. [cite:KhRjivBSwiw:c03] [cite:KhRjivBSwiw:c18]

For each curated memory, retain its source run, version and scope, permit correction or deletion, and record which memories a later run used. A decision record can connect evidence and policy to the plan, tool calls, results and cost; sharing relevant records with other agents or human teammates can make prior work reusable. These records describe observable execution, not faithful access to the model’s internal reasoning. Shared context does not by itself establish safe access controls or improved multi-agent outcomes. In one memory demonstration, the source-run link was partly blocked, and a claimed speedup was not controlled. [cite:TN3mj92oZ8I:c06] [cite:TN3mj92oZ8I:c07] [cite:XPj3mIKEtI4:c02] [cite:XPj3mIKEtI4:c03]

### Let outcomes inform retrieval, cautiously

A trace and a score become useful memory only if a later run can use the lesson. One proposed loop converts evaluated outcomes into guidance for selecting context or broadening a future search. Initially, before enough reviews exist, the described system falls back to semantic search; the source does not establish how many reviews or how much diversity are enough, and noisy feedback can mislead. [cite:Jx4ZFEAq6bY:c01] [cite:Jx4ZFEAq6bY:c07]

In a demonstration, a gaming-mouse search first returned nothing; after feedback pointed to a wireless mouse, a later run searched more broadly and returned related inventory. The informative observation is the changed tool trajectory, not merely a different answer. The example has no held-out test and does not prove the returned product met all gaming requirements. [cite:Jx4ZFEAq6bY:c10]

## Keep long work usable without keeping everything in the prompt

### Recover omitted session material

Compression must preserve a way back to information that a later turn may need. In one reported system, keeping only the first 100 characters made follow-ups lose their referents: after an answer about common inputs, a question about input B looked like a new conversation. An unconstrained model summary also inconsistently omitted important details. These are failures of particular implementations, not proof that all summaries fail. [cite:esY99nYXxR4:c03] [cite:esY99nYXxR4:c04]

The team’s compromise kept the first and last 100 characters of long material, stored the omitted middle, preserved the system prompt and latest results, and exposed IDs, positions and previews for fetching earlier messages or tool calls. This makes omission different from deletion, although the agent must still recognize when to retrieve. The team reported months of usefulness while revisiting the heuristic; neither fragment length nor retrieval accuracy was established as generally optimal. Test follow-ups that refer to earlier results, not just whether the first response fits the window. [cite:esY99nYXxR4:c05] [cite:esY99nYXxR4:c10]

A store of omitted messages within one session is not automatically cross-chat memory. At the time of that account, a new conversation could not recall previously discussed issues; ID storage also did not establish prompt-cache reuse. For execution lifecycle rather than knowledge retention, see [[agent-sessions-and-long-running-work]]. [cite:esY99nYXxR4:c08] [cite:esY99nYXxR4:c10]

### Isolate heavy analysis

A trace-analysis agent can generate more spans while investigating its own failures. Retrying against that growing input can make the original overload worse. One team moved searches over hundreds of spans and intermediate results into a separate subagent context; the main conversation received a compact result and could retrieve more material as needed. This is a context boundary, not evidence that adding agents inherently improves reasoning. The reported improvement was qualitative, and provider-limit failures remained. For coordination choices beyond this boundary, see [[agent-delegation-and-coordination]]. [cite:esY99nYXxR4:c02] [cite:esY99nYXxR4:c07]

## Turn experience into maintained knowledge

A memory lifecycle can ingest an experience, extract candidate facts, consolidate them, and retrieve the resulting information later. Different records serve different purposes: a critique and a user’s accepted exception can help a later polishing session, while a prior failed query can inform a shared organizational librarian. Human overrides, low-confidence moments and clarifying questions can identify candidate guidance updates. None of these observations proves that an entry is correct, current, or safe to generalize; the reported systems do not establish a universal consolidation policy or quantified improvement. Updating surrounding guidance is not necessarily updating model weights. [cite:32nrHU6zHU8:c02] [cite:SQMCtZX3trg:c05] [cite:YZQsWVeN3rE:c06] [cite:jJQoVkd5yLg:c08]

### Combine examples, rules and review

Episodic memory offers a particular previously labeled case as a reference. Semantic memory states a reusable rule, such as a customer-specific distinction clarified by reviewers. They complement each other: retrieve a genuinely comparable precedent, apply the current rule, and send an unresolved or poorly matched case to a person. The proposed allocation depends on retrieval and escalation identifying those cases correctly; the source gives no verified similarity threshold. Customer-specific security judgments should not be generalized into universal policy. [cite:wEc9aG7cRQc:c04] [cite:wEc9aG7cRQc:c05] [cite:wEc9aG7cRQc:c06]

Persisted errors can repeatedly mislead. Offline consolidation can compare memories with prior traces, correct false or overly local conclusions, and retain abstractions useful beyond one task. A selected Pokémon example reports five of five raw-memory runs falling through a trapdoor after a wrong location was stored; an offline correction enabled progress in the illustrated case. This is not a general success rate. A comparison of different model generations also suggests that the ability to write useful memories matters, but does not isolate model capability as the cause. Evaluate the quality and compute cost of consolidation in the actual application rather than assuming a net gain. [cite:9QebvrrY3KY:c05] [cite:9QebvrrY3KY:c06] [cite:9QebvrrY3KY:c07] [cite:9QebvrrY3KY:c10]

### Close gaps without exhausting experts

Use a concrete task to expose a missing definition or procedure, ask the responsible expert targeted questions, and curate the answer so the next task can retrieve it. One demonstration used prepared answers and flat files standing in for enterprise systems; it is not evidence of enterprise-wide completeness. An audience concern was that agents can keep asking follow-ups and overload staff, while tickets themselves may be incomplete. The speaker therefore favored starting with one small team and an available expert, bounding the questions, and repairing context offline before operational retrieval. The reported couple of weeks concerned discovering gaps, not necessarily filling them. [cite:_QAVExf_1uw:c02] [cite:_QAVExf_1uw:c09] [cite:_QAVExf_1uw:c12]

Observed user demand can expose a different gap: one sales-assistant account describes using frequent questions and product material to create enablement content and return it to retrieval. The account does not demonstrate content approval, factual checking, or a measured accuracy gain. In a separate reported banking incident, a changed interest-rate policy had not reached the vector index; traces led the team to repair freshness instead of replacing the model. For source ingestion and external provenance, see [[retrieval-evidence-and-provenance]]. [cite:DrTdD-ttjCY:c11] [cite:ObTPqBGsEbA:c11]

## Design and distribute reusable procedures

A skill or playbook packages instructions for an applicable kind of work. Keep a maintained map to current authoritative documentation for volatile details, rather than duplicating an entire changing API reference. Conversely, keep stable safety-critical guidance visible where it is needed: agents may skip a reference. An example product workflow changes a database schema in development or staging, runs security and performance advisors, fixes their findings, and only then creates a migration. It is not permission to make unrestricted production changes. [cite:JT3OzDKrucU:c03] [cite:JT3OzDKrucU:c05]

Route instructions by task and audience. For example, a rule favoring distinctive typography on a brand landing page may conflict with a native-feeling product interface; separate instructions avoid turning either into a universal ban. The reported benefit is not a quantified comparison with a monolithic prompt. Relevant accessibility guidance should be reliably loaded for UI generation, but the cited recommendation did not demonstrate a complete mandatory-loading mechanism, and instruction exposure is neither enforcement nor a substitute for manual accessibility testing. [cite:SQMCtZX3trg:c04] [cite:ZccJsdOE54M:c08]

Task-specific catalogs can preserve confirmed patterns and antipatterns across projects and model changes. A shared human-readable repository may be sufficient to start; a vector database is not mandatory. Bringing confirmed knowledge into authoring or review earlier is a proposal that may also increase latency and context cost. One practitioner’s build-versus-buy heuristic favors buying generic infrastructure and building local practices, while acknowledging ambiguous cases rather than proving a cost advantage. [cite:CgsWxRUY5Eo:c05] [cite:CgsWxRUY5Eo:c07] [cite:dSg0pu8d6qg:c14]

Content portability is not distribution compatibility. Repository packages, plugins and central services are different ways to make skills discoverable, and some formats are environment-specific. A described central service selects organizational skills by query and role; verify actual client support and policy behavior instead of assuming universal compatibility or always-current delivery. Version packages and their dependencies so a procedure matched to one product version is not silently applied to another. [cite:JT3OzDKrucU:c10] [cite:u-o0sW9nwmk:c04] [cite:bSG9wUYaHWU:c06]

### Distill a skill from evidence, not just a topic

Choose a coherent source scope first: a conversation, an entity-centered subgraph, or another bounded collection may fit better than an entire workspace. Structural processing can organize that source while limited language generation synthesizes descriptions. In one described pipeline, most steps were asserted to be deterministic, but the full pipeline and its reliability were not independently established. [cite:XPj3mIKEtI4:c06] [cite:XPj3mIKEtI4:c07]

Check support for each instruction and step, not just whether the overall topic has sources. A patient-intake demonstration linked a previously generated skill’s steps to tool calls and entities; it did not show successful execution or clinical validation. If the selected graph spans unrelated communities, splitting the skill may improve coherence, but community detection is only a heuristic and step-level provenance alone cannot prove completeness. [cite:XPj3mIKEtI4:c08] [cite:XPj3mIKEtI4:c09]

## Operate knowledge as a maintained system

### Ownership, versioning and freshness

Assign knowledgeable owners to shared instructions, review changes, and update or retire skills when products or workflows change. An accessibility specialist maintaining a reusable skill is one reported example; another account notes that writing a review skill is much easier than running it consistently and economically at scale. A large experimental collection can be useful locally while a production environment carries only the maintained set it needs. A repository and pull-request review are one collaborative option, not proof that repositories outperform other stores. [cite:I2LL_wd89-A:c03] [cite:EL123UNokkI:c10] [cite:GmAQKINjv1E:c14] [cite:_QAVExf_1uw:c06]

Version not only the skill text but also the relevant instructions, source material, model and configuration used in a run. For each change, record the failure that prompted it and the intended correction; a diff without rationale may be hard to interpret later. Versioning enables comparison and rollback, not deterministic replay across changing models or proof that a new rule is correct. [cite:ObTPqBGsEbA:c08] [cite:IJXjTLPzvAU:c06]

Age and duplicate flags identify candidates for review, not truth: an old document may still be correct and a newly updated one may be wrong. Track dependencies from skills to their underlying evidence, and flag changed, removed or contradictory sources; the proposed mechanism does not prove automatic repair. Keep graph edges and evaluation expectations current too: in one impact-assessment case, new consumers appeared between an evaluation’s authoring and execution. A newer model can also confidently repeat an obsolete product reference. Check current documentation and retire stale or irrelevant context rather than assuming a model upgrade fixes it. [cite:_QAVExf_1uw:c11] [cite:_QAVExf_1uw:c13] [cite:XPj3mIKEtI4:c10] [cite:k2ClBT4aqAg:c07] [cite:Lrw0jqBNaw0:c06] [cite:KA5kPbdkK2E:c05]

### Repair procedures from feedback

Review recurring failures, corrections and trace patterns for a specific reusable lesson; propose a change to the applicable playbook, have an owner review it, and make the reviewed version available to later runs. One team reported putting reviewer steering in a version-controlled feedback file loaded into subsequent runs. The account does not quantify recurrence reduction or explain conflict resolution. A skill update described for new sessions does not establish that already-running sessions receive it automatically. [cite:xIt_mTQp6mY:c09] [cite:FGftGOzfohc:c07]

Track whether rules are used and whether users find them useful, not just how often they fire; frequency alone is not validated utility. Failure-triggered repair avoids routine probing cost but discovers drift after a user-visible failure. Scheduled sample runs or audits can find problems earlier at ongoing cost; the cited healing and audit workflows are proposals or working theories, not established guarantees. Production-derived regression sets have a separate lifecycle: [[build-and-maintain-production-grounded-evaluation-sets]]. [cite:s-aixZYJG4c:c09] [cite:p7gaxmCUiIU:c09] [cite:6MudaeKdBSk:c14]

Reserve capacity for this work. Agent and harness failures compete with feature delivery, and their timing and repair effort are hard to predict. Explicit prioritization can help avoid maintenance being silently dropped or displacing a deadline; the evidence does not prescribe a staffing percentage. [cite:X6l4lpA0_NY:c07]

### Choose stores and protect what they contain

Choose the simplest inspectable substrate that supports the required scope and operations. One team reported a separate Markdown file per user, capped at 8,000 characters and updated after sessions; that is a local design, not a validated universal limit. Files and databases can both offer programmable memory, and one speaker found overly prescriptive schemas restrictive in their setting; this does not mean structured schemas always fail. User and organizational stores can be combined, but export through an API does not prove a drop-in migration, and the cited account does not specify authorization or tenant isolation. [cite:YIhvrvHtonk:c05] [cite:9QebvrrY3KY:c09] [cite:FGftGOzfohc:c11]

Workflow definitions themselves may disclose valuable institutional procedures, not just the data processed by them. Private deployment with approved models is an option when appropriate, but keeping textual workflows on premises does not by itself establish privacy, security or regulatory compliance. Apply the relevant access and isolation controls separately: [[agent-authority-isolation-and-runtime-controls]]. [cite:7T-gldvgfpo:c11]

### Give experts and recurring work a durable home

Domain owners should be able to maintain the logic they understand. In one reported pipeline, a clinician could add a customer-specific intake-form skill without an engineering code change. That illustrates an editing interface, not a complete clinical governance process, skill schema or regression suite. Expert ownership still needs reviewed changes and appropriate verification. [cite:XAsb7MIAzm8:c11]

For recurring work whose desired output is understood, bind a reusable procedure or contract to an event or schedule. Start with one bounded job—such as a proposed weekly flaky-test hunt—rather than forcing an exploratory, one-off question into a fixed obligation. A CI iteration that produces a reviewable change is a possible hosting pattern, but the cited example does not provide complete security or authorization controls; triggering a job is not approval to deploy its output. [cite:7T-gldvgfpo:c04] [cite:7T-gldvgfpo:c10] [cite:X6l4lpA0_NY:c11] [cite:xIt_mTQp6mY:c08]
