A user reports that an agent gave an unhelpful answer. The final response alone cannot tell you whether the agent never called a needed tool, called it with the wrong arguments, received empty results, or ignored useful evidence. A trace connects the interaction to the steps that actually ran, making those competing explanations inspectable. It is evidence for diagnosis, not proof that the user’s task succeeded or that every relevant event was captured. [cite:JsCCrBF7F1g:c01] [cite:0RNNfxpdbQk:c02]

## Capture the execution you need to explain

Treat a task or conversation as a parent trace and the model calls, tool calls, retrievals, and other meaningful operations as nested spans. At each important boundary, capture the input and output or a safe reference to them, the operation’s identity, timing, status, and relevant state changes. Record prompt and model versions, settings, tokens, retries, and costs per attempt. Network logs alone miss local retrieval, in-process tools, and memory operations; instrumenting semantic nodes makes those steps visible too. [cite:Lc8zRh9muoY:c04] [cite:ZdheJTfLu-s:c06] [cite:8g1N_a3h9H0:c02]

Keep enough context to connect an operation to the user's goal, the available tools, prior steps, and any stated reason for the action. These annotations help formulate hypotheses, but an agent’s explanation or reported belief is not verified access to the model’s internal causal reasoning. For a browser workflow, also capture what happened in the browser: a plausible decision log cannot establish that navigation, a download, or a click actually worked. Make the resulting sequence legible to product and support staff as well as engineers. [cite:32nrHU6zHU8:c05] [cite:5xi_S1f9sDU:c07] [cite:ON5LIT0M4do:c03]

Correlate components using trace context and relevant domain identifiers: an interaction ID can link a user request to its specialists and dependencies; a payment ID can connect intent, the seller called, and its response. Check context propagation at process boundaries. In one case, passing the parent span ID into a coding-agent subprocess exposed turns and commands that had been orphaned; that solution is an example, not a universal propagation contract. Trace repair agents as well as the application when they investigate or change it. A missing child span remains a visibility gap, not evidence that no action occurred. [cite:T3SS931wU0I:c08] [cite:YU1uD_YkpjU:c11] [cite:ImnZ7s68jw8:c10]

### Make evidence queryable and replayable

Attach evaluation results, classifications, and version or task metadata to the trace that produced them. A decline in a quality score can then lead to the individual spans behind it: for example, did a model stop calling the intended tool, or did the tool run and return bad results? Count adoption alongside answer quality and cost; using a tool is not the same as benefiting from it. Query labels to select candidate cases, then inspect inputs, outputs, and contrasting successes. A workshop demonstrated this query-and-drill-down workflow on prepared support traces; filters cannot find unlabelled failures reliably and do not make the retrieved cases representative. [cite:iOXM3zE-2dk:c03] [cite:KhRjivBSwiw:c10] [cite:hfEczxdNyvU:c11]

For a hard-to-repeat failure, preserve the recorded decisions and state transitions rather than demanding that a new model call reproduce the same text. Reconstruct the old run, or substitute recorded outputs at selected boundaries while inspecting the remaining behavior. This is useful precisely because a fresh generation can take a different path. Selective replay still depends on what was recorded: live tools, unrecorded external state, or unstubbed model calls can change the result, so it is not automatically deterministic. [cite:Lc8zRh9muoY:c03] [cite:Lc8zRh9muoY:c04]

### Findings must tell someone what to do

When a check blocks a workflow, retain the failed gate, the contract it tested, the reason, and the evidence needed to investigate. Deliver a proposed remediation in the place the responsible person works—for example, alongside a change under review—and preserve a machine-readable finding for issue or security workflows. A readable report helps action; neither its structure nor the gate’s decision proves the underlying finding is correct. [cite:WLXxTaPagA8:c09] [cite:iKQ78wyJEXU:c06]

Apply the same discipline to CI. Distinguish a suspected flaky test from an infrastructure failure or a likely code defect before responding. A retry may unblock a change but does not repair the flaky test, and an automated classification can be wrong. Aggregate failure categories across changes to decide whether test reliability or infrastructure deserves investment; counts of feature, fix, and refactor PRs describe workflow allocation, not business value. [cite:uuwDWRbxoYo:c05] [cite:uuwDWRbxoYo:c10]

## Move from individual traces to operational patterns

One successful trace is not a picture of production. Compare branch frequencies and their latency, retries, and quality signals; then open examples from both common and rare routes. A rare branch can hide a serious defect, while a frequent but mildly inefficient route can dominate cost. Observed frequencies are only estimates for the traffic and period captured, not permanent properties of the system. [cite:JsCCrBF7F1g:c02]

Track economics at the same task and span level. A cheap model call may produce a costly task if it requires many more calls or tool steps. Record input and output tokens, cached tokens, per-step timing, model selection, and whether interventions such as summarization actually occurred. Tag costs by feature, tenant or organization where appropriate, provider, and environment so teams can compare workloads rather than guess from the total bill. Combine those measures with task-specific quality evidence before deciding on routing, limits, or procurement; cost attribution alone does not establish quality or reconcile a bill. Cost and replay overhead can remain unpredictable even with managed infrastructure. [cite:4n08JHb90hI:c02] [cite:WP3hjUXd918:c05] [cite:rTojoVotlD8:c05] [cite:32nrHU6zHU8:c10]

Compare a change in failures or latency with an appropriate historical baseline, including workload and load, then overlay model, application, dependency, and configuration changes. This gives an investigator a narrower set of hypotheses—not a proven cause. A change coinciding with a spike might be unrelated; check the affected path and contrasting cases before assigning blame. The proposed baseline-and-change approach in the source does not establish detection thresholds or early-warning accuracy. [cite:YNT7Plf9KIg:c04] [cite:YNT7Plf9KIg:c05]

### Store useful evidence without creating a new exposure

Detailed traces may contain conversation text, nested tool results, or media and must support both fresh incident lookups and large historical searches or annotation. Test those different workloads against actual data and latency needs; a vendor’s scale claims do not establish the right database for every team. Operating a trace platform also means maintaining access controls, masking, and retention—not just displaying a dashboard. [cite:mUQoVz7THu0:c06] [cite:mUQoVz7THu0:c07] [cite:mUQoVz7THu0:c08]

Collect only what a diagnostic purpose warrants. A user can paste sensitive information into free text even when a separate secure collection flow exists. Where possible, remove or mask sensitive input before it reaches retained telemetry; restrict access and test the full capture path, including downstream copies. A proposed scrubber is not a universal guarantee that nothing sensitive will be stored. [cite:1tpqdglI3T0:c11]

## Find issues, then identify the responsible layer

Start with a change in a known failure category, a deterministic indicator such as a keyword spike, or a broad signal such as user frustration. Use it to retrieve and read examples, including cases the signal may have missed. Inspect cases independently and cluster recurring patterns; domain experts can reject false positives, intended behavior, or irrelevant clusters before work is assigned. Deep inspection can yield cheaper indicators—specific content patterns or tool sequences—for ongoing surveillance. Those indicators inherit the blind spots of their definitions. [cite:jHMiYtjoJfA:c10] [cite:-aM2EDTiaMs:c11] [cite:aHhB3sjGjkI:c05] [cite:aHhB3sjGjkI:c06] [cite:pSto5YaNGUo:c07]

Make an issue a persistent, reviewable record of a suspected repairable mechanism, with supporting and counterexample traces, onset, affected-user share, severity, and owner. Deduplicating occurrences reduces noise, but do not equate a semantic cluster with an issue: wrong price quotes and wrong refund calculations can look alike while requiring different fixes. Clusters can also drift over time, so revisit their boundaries and distinguish a new mechanism from a recurrence. Prioritize prevalence and impact, while retaining rare high-severity cases. [cite:UGuNt2_Oz8s:c03] [cite:jHMiYtjoJfA:c06] [cite:jHMiYtjoJfA:c08]

**Worked source example — planted defect.** In a shopping-agent demonstration, searches used human-readable category names while the stored values were lowercase hyphenated slugs. The trace showed empty results and fallback searches; inspecting the tool arguments alongside the repository’s data contract pointed to normalization, rather than necessarily a weak model. A candidate repair can be checked against the recorded case and other relevant cases. This was an intentionally planted workshop defect, not a measured production failure rate. [cite:UGuNt2_Oz8s:c02]

Use that sequence as a diagnostic habit, not a fixed answer: compare the request and tool arguments, the actual result, the implementation or service behavior, and the final outcome. A bad result might come from an incorrect prompt example, a tool interface, sandbox execution, an upstream provider, an inference failure, or a product expectation the system never supported. Route a supported model gap to model evaluation, an interface or infrastructure defect to engineering, and a missing capability or expectation mismatch to product. Do not infer that every bad answer is an engine bug, or that an accessible sandbox automatically explains a failure. [cite:HEFSExa0xl0:c12] [cite:k72eLcYpVys:c06] [cite:btxG75rNJC4:c01] [cite:Emo5FGGY-wM:c04]

## Run diagnosis as an operational loop

An incident playbook connects detection to an accountable responder, trace-based diagnosis, containment, repair, and regression checks. If appropriate for the service, containment might mean rolling back a change or routing affected work to a person while the cause is investigated. Join the report and trace to the relevant code or dependency; write down the hypothesis, supporting evidence, missing context, and assumptions. Persist intermediate artifacts so another investigator can resume or challenge the analysis. A coding agent can prepare evidence or a proposed fix, but a plausible report is not a verified diagnosis, and larger fixes may need human leadership and review. [cite:ObTPqBGsEbA:c12] [cite:pSto5YaNGUo:c08] [cite:L2r6vLlLgs8:c08] [cite:9HbzAWnKbo4:c04]

Choose the trigger to match the question. An engineer can investigate on demand; a periodic sweep can find patterns that no single alert captures; a quality, latency, or cost alert can initiate a faster targeted investigation. A short-window monitor for stuck sessions and a slower cross-session analysis answer different questions, so use both when warranted. Set thresholds and cadence for the application rather than copying a demo threshold. The described modes have not been shown equally reliable or inexpensive. [cite:fnuNVFgLjHA:c05] [cite:fnuNVFgLjHA:c12] [cite:kZsf_Sfm7RU:c06]

After repair, feed the diagnosed case and its relevant variants into offline development and regression evaluation, then continue reviewing live usage for new patterns. Post-merge observation can reveal surprises tests missed, but cannot undo an irreversible action or replace preventive controls. Code throughput and deployment counts are activity or downstream signals, not proof of stability or user benefit. For how to maintain production-grounded cases, see [[learning-from-production]]; release decisions have their own owner in [[production-governance-and-release]]. [cite:pSto5YaNGUo:c01] [cite:eAXxdtNlK04:c08] [cite:_mi3alkqy4s:c10] [cite:ZpK5PWX2YRM:c05]

### Read success and feedback carefully

A tool returning HTTP success may still return empty or irrelevant content. A completed task can have a wrong price or fail the user’s actual intent; a successful final answer can also conceal repeated failures and lucky recovery. Examine the content and intermediate struggles as well as availability and error status. A toy shopping demonstration exposed empty results despite successful spans; its small uncontrolled results do not establish a production failure rate. [cite:F0TNSmbo5hE:c04] [cite:kZsf_Sfm7RU:c02] [cite:kZsf_Sfm7RU:c03]

Collect reviewer overrides, their reasons, and feedback on cited evidence in the normal review workflow. Changes in override frequency or review time can direct investigation, but an override is not automatically a correct label, and a long review may have several explanations. Likewise, clicks, copies, and user ratings are behavior or feedback signals, not correctness measurements. [cite:T0HhO4YtTfE:c06] [cite:T0HhO4YtTfE:c08] [cite:gonAewBZxfU:c11]

Repeated requests, complaints, and abandonment can suggest a user is stuck; absence of further messages does not establish resolution. Investigate whether the task is supported but needs better guidance, or whether the product has a bug or missing feature. For sessions genuinely resolved, examine what information would have helped earlier, generalize across similar examples, and have reviewers check the proposed guidance before introducing it. That is a reported workflow, not proof that guidance caused the observed outcomes; ongoing knowledge maintenance belongs to [[reliable-agent-context-and-memory]]. [cite:KA5kPbdkK2E:c01] [cite:KA5kPbdkK2E:c02] [cite:KA5kPbdkK2E:c03]

Agents can also report environmental friction: a selective feedback tool may surface missing tools, conflicting instructions, or platform failures, while an end-of-run retrospective asks every run and may find issues a thresholded report omits. Neither method has a demonstrated universal signal-quality advantage. In one reported case, continued complaints after a filename fix exposed non-breaking spaces that ordinary-space handling had missed; developers reviewed proposed fixes. Spikes in complaints can be incident leads, but fallible, incomplete self-reports do not replace independent monitoring. [cite:KA5kPbdkK2E:c07] [cite:juoNbJiZUi0:c05] [cite:KA5kPbdkK2E:c08] [cite:KA5kPbdkK2E:c09] [cite:KA5kPbdkK2E:c10]
