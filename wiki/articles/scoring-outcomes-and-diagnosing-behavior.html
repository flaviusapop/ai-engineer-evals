Agent evaluations

Verifying agent outcomes and diagnosing behavior

Covers score surfaces and diagnostic traces, not verifier security or environment fidelity.

Download Markdown

On this page

  • Test discovery, activation and task outcomes separately
  • Probe predicted state separately from action success
  • Verify the outcome, then inspect consequential actions
  • Diagnose the tool loop and stopping behavior
  • Evaluate orchestration, routing and deployment
  • Use a verifier to steer without confusing it with an evaluation

A fluent completion message is not the same thing as a completed task, and a correct result does not show that the agent acted safely. Evaluate the resulting state, consequential behavior and operational cost as distinct dimensions. The distinction leaves room for legitimate unexpected solutions while exposing failures that a single pass/fail score hides.

Test discovery, activation and task outcomes separately

For an instruction-based skill, construct positive requests where it should load and negative requests where it should not. Inspect invocation as a routing signal, then separately check the resulting artifact or task outcome. Overlapping descriptions can cause a missed trigger; broad descriptions can cause irrelevant loading. An invocation assertion may break when a skill is renamed, even if the workflow still works. Nor should a task-success test automatically demand loading on the first turn: a later load or another valid approach may achieve the objective. [1] [2] [3]

Guaranteed instruction injection and normal discovery answer different questions. Injecting the skill tests behavior given exposure; installing it in a fresh environment and letting the agent find it also tests installation, metadata and selection. That organic setup was proposed, not demonstrated in the cited workshop, whose injected demonstration also had a faulty grader. Iterate on actual cases, inspecting each run and rerunning behavior and artifact checks after revisions. Five to ten initial runs are a practical starting heuristic, not a reliability or representative-coverage threshold. A small repository instrumentation suite used a language-model judge without reported calibration. [4] [5] [6]

One team compared six scenarios across four agent-model combinations with no MCP or skill, MCP alone, and MCP plus skill; its completeness rubric and repetitions were insufficiently specified to reproduce the result, and there was no skill-only condition. Another vendor reported a rise from 36% to 100% after distilling a skill for one Chromium-on-Lambda task, without sample sizes, independent trials or held-out variation. Neither establishes a general improvement. For controlled comparison design, see Comparing agents without confounding the result. [7] [8]

Probe predicted state separately from action success

A proposed world-model probe recovers a computer state at a specified fork of a recorded run, presents a defined amount of prior context to the model, and asks it to predict a particular reward, internal state, or observation. Compare the prediction against the corresponding recovered or subsequently observed target, with the fork time and target semantics specified in advance. An evaluator can then distinguish predicting the state from successfully choosing actions; success at either does not establish the other. This is a proposal, not a measured accuracy result: no probe dataset or exact replay guarantee is supplied. World fidelity is a separate problem: Building and validating simulated agent worlds. [9]

Verify the outcome, then inspect consequential actions

Define the desired external effect before scoring. For a hotel booking, check the actual reservation and its names and dates, not just the agent's confirmation. A tool acknowledgement, user-visible delivery and durable storage are different observations: an internal message can be accepted but not rendered, while delivery and persistence can also fail separately. Choose the boundary relevant to the task and do not assume a receipt or file fingerprint proves its contents are correct. The hotel source identifies dimensions, not a complete scoring formula. [10] [11] [12]

Where persistence matters, verify state after reload or through an appropriate API or database. In a waitlist demonstration, the entered email appeared but vanished on reload; the later repair was not shown passing. A payment review identified process-local refund replay state, which could behave differently after a restart or across processes, but did not demonstrate that failure. A state check does not prove a user reached the result through the intended interface; some browser-only tests deliberately exclude database access to preserve that boundary. See Testing product behavior and visual regressions. [13] [14] [15]

If an evaluator must consult an external system, use task-appropriate access: read-only inspection of logs or a sandboxed execution environment are proposed patterns, not validated safety guarantees. A second model can inspect a completed form and return problems for correction, but its opinion is not proof of accuracy. Review and approval should match the stakes and concern the final artifact, not merely an earlier draft. [16] [17] [18] [19]

A valid alternative route should not fail simply because it differs from the designer's itinerary. But the correct flight booked in a prohibited fare class is still a policy failure. Check identity or permission requirements, ordering dependencies and consequential actions separately from outcome and cost. Where an action is unambiguous, an executable assertion—for example, checking that a required concession was actually granted—can provide a clear signal alongside subjective assessment. Do not turn this into an exact tool sequence for every task. [20] [21] [22] [23]

Diagnose the tool loop and stopping behavior

Inspect the inputs available at each decision, tool choice and arguments, returned errors, subsequent corrections and the eventual state. In one financial-query demonstration, a model guessed a nonexistent table and then an answer; another trace listed tables, inspected the schema, made a query error and used the error to repair it. These are individual vendor-reported traces, not a universal model ranking. Also test whether the harness actually exposes an interactive terminal prompt: a redraw loop visible to the agent instead of the question can look like a reasoning failure. [24] [25] [26]

Trace inspection should begin with a question such as where progress stopped or whether a tool returned the right artifact. One team found a tool returning incorrect file paths despite an attractive benchmark ranking; repair the harness and rerun before attributing the result to agent capability. A selected run that worked actively for more than three hours without solving its task illustrates why runtime is not progress. Traces suggest hypotheses, not unique causes; a counterfactual model comparison requires actually running the alternative. [27] [28] [29]

Do not infer completion from any text-only turn: a model may announce an action before making its tool call. One reported harness instead requires an explicit finish call, rejects it while plan items remain up to three times, warns near its iteration limit, and can force a finish. Record whether the run completed, was forced to stop, or paused for user confirmation; these are different outcomes. The same team moved plan bookkeeping into the harness after observing excessive checklist updates, but this is contextual experience, not a universal optimum. [30] [31]

Evaluate orchestration, routing and deployment

A graph can constrain planning to predefined branches and make supported flows more predictable, but accumulating special cases can make unfamiliar requests brittle. Test the contracts between nodes, classifier decisions and retry loops as well as individual nodes and out-of-distribution requests. For labeled routing destinations, a confusion matrix with class-sensitive precision and recall reveals which branches get confused; the multiclass extension is suggested rather than validated. Tool retrieval has a similar failure surface: a flight request should expose relevant flight tools, but an omitted necessary tool and the fallback behavior need testing too. The flight-versus-weather example is illustrative, not a production-accuracy result. [32] [33] [34] [35]

Model routing is another decision: compare candidates on the actual task classes, required quality, cost and operational constraints. An internal sidecar ran agents across models and reported cheaper routing opportunities for UI work, but did not disclose its judging criteria, sample size or cost accounting; it is not a universal model ranking. [36]

Specialist agents are justified by distinct capabilities, not by agent count. In one described design, a perceiver handles video understanding, a retriever finds material in a corpus, and a reviewer orchestrates the work and applies temporal reasoning. Inspect what the perceiver passes onward, whether the retrieved material is relevant, and whether the reviewer uses those inputs correctly; a good final answer alone can conceal a weak handoff. Compare the decomposition with a single agent on the actual task, including outcome quality and coordination cost. Another product reportedly moved from multiple specialists back to one agent with on-demand skills; neither design experience is a controlled comparison. [37] [38]

Exercise the complete deployed system, not just a model in isolation: introduce relevant retrieval errors and tool failures, test permission boundaries, check whether human review catches errors, and observe recovery. Remote invocation can include actual coordination code, but the cited demonstration did not specify isolation, side-effect safeguards or tool-state control. Include regression traps where a fix for one policy harms another: a fictional support benchmark tests fast eligible refunds while preserving generosity thresholds, but its reported baselines conflict and finite tests cannot prove all historical behavior is preserved. [39] [40] [41]

Use a verifier to steer without confusing it with an evaluation

A runtime verifier can check measurable criteria after each attempt and feed specific failures back to an agent for another iteration. In a parameter-golf research demonstration, managed agents iterated until the stated criteria and 20 iterations were met; no numerical comparison was supplied. This is a steering mechanism, not independent evidence of generalization. A narrow verifier can be passed while the underlying task remains incomplete; assess the resulting system on separate tasks and evidence, using Tests, oracles and verifier validity for verifier validity. [42] [43]
