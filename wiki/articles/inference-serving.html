Efficiency and performance

Measuring inference serving performance

Covers inference phases, metrics, concurrency and KV capacity, not user-facing voice or specific decoding techniques. Service performance and resource provisioning, not business ROI or kernel algebra.

Download Markdown

On this page

  • Diagnose the request and its metrics
  • Sweep load against the SLO
  • Budget memory and place the phases
  • Schedule workers and provision readiness
  • Compare hardware and rental exposure on common terms

A serving configuration has no single meaningful speed. Its capacity depends on the request mix, concurrent demand, hardware, scheduling and the latency users can tolerate. Measure it under the workload and service objective you intend to operate, rather than choosing the largest isolated tokens-per-second number.

Set interaction-dependent latency objectives

Start with the interaction. Immediate review may require a tighter deadline than a coaching response where users accept a longer wait for better reasoning. Choose a measurable event and a percentile objective as well as acceptable quality and cost; a mean completion time does not guarantee a good tail. A model's first token may itself be reasoning rather than a usable answer. For speech, time to first audible response includes more than model serving; see Interactive latency for those boundaries. [1] [2]

Also compare delivered words for the languages users actually speak. Tokenizers may use different numbers of tokens per word across languages, so equal token throughput does not imply equal time to words. That observation comes from a speaker's account, not a controlled universal comparison. [3]

Diagnose the request and its metrics

Prefill processes the input and builds attention key-value (KV) state; decode generates subsequent tokens with dependencies on earlier tokens. Record prompt and output lengths and repeated prefixes to determine which phase dominates. Long-document analysis with a short answer can be prefill-heavy; long generation puts more weight on decode. Speeding decode alone does not remove long-prompt processing. Prefix reuse is a separate design decision; see Managing context, retrieval and cache costs. [4] [5] [6]

Track at least time to first token (TTFT), inter-token latency or per-request generation rate, end-to-end completion latency, and aggregate request or token throughput. These answer different questions: throughput is total work delivered, not the pace experienced by a single user. In one speaker-reported low-reasoning test, raising concurrency from 32 to 64 produced about 1.9 times the throughput but sharply worsened P95 TTFT; exact tail times are not reliably available. A separate dashboard demonstration changed batch-token settings and saw inter-token latency change with little first-token change. Neither result is a universal tuning rule. [7] [8]

Sweep load against the SLO

Construct a representative workload including prompt and output distributions, prefix repetition, arrival pattern and expected concurrency. Keep model, precision, hardware, replica count, workload and objective explicit when comparing a candidate with a baseline. Sweep offered load and relevant serving settings, recording achieved throughput and latency percentiles at every point. The knee is where additional load no longer produces proportional throughput while latency rises; the safe operating point can be below it if the SLO is already violated. A knee belongs to that configuration and workload, not to the model in general. [9] [10] [11]

Illustrative decision: for an interactive document assistant, compare two configurations using the same long-input/short-output trace and a chosen P90 TTFT deadline. Reject a higher-throughput configuration if its P90 violates that deadline; among conforming points, compare completed load and cost. Repeat at the intended replica scale and check answer quality when changing numerical precision or the model. This is a decision procedure, not a measured result or a claim that a single SLO captures the whole product. An eight-replica code-generation comparison illustrates the importance of the scale and baseline, but its available account lacks full hardware and repeated curves. [12] [13]

The load generator itself must be measured. Record scheduled versus actual send times and delivered requests per second, client CPU and streaming collection delays, alongside server-side timestamps. In one incompletely specified experiment, a requested 200 QPS became only 38 QPS because of client limitations; another reported substantial client-side streaming delay. Central scheduling with multiprocess execution is one design for reducing client contention, not a server optimization. Test the generator independently before treating an apparent server knee as real. [14] [15] [16]

Budget memory and place the phases

Weights are only part of the accelerator memory budget. Concurrent requests also retain KV state for system prompts, user inputs, tool results and generated tokens. Estimate using actual length distributions and simultaneous demand, then load-test: an advertised maximum context window is not the same as every request's typical memory requirement. A hierarchy can hold hot KV blocks on GPU and colder blocks in CPU memory or disk, trading capacity for transfer time. [17] [18]

Prefill and decode may be placed on different hardware to suit their different demands, but the KV state must be located and moved between them. Compare any phase-specific benefit with transfer and scheduling overhead at the actual request mix; the described heterogeneous placement is an architectural proposal without a measured head-to-head or cache-transfer cost. It is not caching a final answer. [19] [20]

Schedule workers and provision readiness

For many small, fast requests, one described design puts annotated requests in a shared queue; workers pull work and form batches using local capacity rather than depending entirely on possibly stale central worker state. Keep gateway processing lightweight and large payloads outside the queue. If a worker pulls too many items, returning them over the network costs time; local coordination among colocated GPUs is one proposed remedy. The source does not establish its fairness or measured latency. [21] [22] [23]

Small models introduce a separate residency decision: dedicated warm pools for each model may waste capacity, while sharing a GPU can require pinned popular models plus lazy loading and eviction under memory pressure. That is a proposal without a detailed policy or measured outcomes; test load-time delays, memory contention and scheduling behavior for the intended mix. [24]

For procurement, compare usage pricing with dedicated capacity against measured baseload, allowed bursts and utilization; dedicated hardware is not automatically cheaper when idle. Readiness matters too: in computer-use workloads a GPU can wait while a large sandbox starts or resets. A demand-sized warm sandbox pool can move preparation ahead of need but pays for unused environments. Evaluate resource prices, startup delays and pool utilization rather than assuming savings; the described pool provides no measured hit rate or break-even. Runtime image size can similarly trade cold-start time against steady-state performance. [25] [26] [27] [28]

Compare hardware and rental exposure on common terms

Compare accelerators on the same model, request mix, quality, latency objective and achieved utilization—not on relative speedup alone. Include service scope, networking, energy, software and operating costs: a managed cluster and bare-metal rental can leave different work with the buyer. More output at the same interactivity can improve capacity economics, but optimization and maintenance also cost money; a GPU hour is an input, not an acceptable completed task. [29] [30] [31]

If using a rental-price reference, inspect its sampled providers, service and contract terms, and whether it represents offers or completed trades; neither necessarily equals your realized rent. A proposed rent hedge depends on how changes in the reference move with changes in your own price, not just on similar price levels. This is a market-design argument, not a validated hedge or protection against operational risk. [32] [33]
