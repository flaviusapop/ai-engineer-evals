Verification and assurance

Building verification feedback and integration gates

Owns orchestration, repository readiness and integration gates, not the detailed test oracle.

Download Markdown

On this page

  • Give the agent access to the actual behavior
  • Return failures, repair, and recheck
  • Make workflow transitions enforce checks
  • Separate shared enforcement from project policy
  • Plan reviewable slices and preserve state
  • Isolate parallel work and validate the landing combination

A coding agent can say it has finished while never running the application, or it can pass a local test and still break the shared branch. A dependable workflow makes verification executable during the work, returns useful failures to the agent, and requires checks again at the boundaries where other people and changes become involved. An integration pass means the configured gate passed on a particular artifact; it is not proof that the work satisfies every product requirement.

Give the agent access to the actual behavior

Start with the acceptance behavior and provide a way to exercise and observe it. For a web interface, this might mean a browser, test accounts and application logs; for an API, direct requests and relevant server state may be more useful. A test workflow can separate planning scenarios, generating tests and repairing tests, but a described test-healing role is not evidence that repairs are reliable. A screenshot can help inspect a screen; it cannot establish every functional or permission property. [1] [2] [3]

The internal Spoolside interface described for a VS Code extension exposes screenshots, compressed snapshots, frontend and backend logs, restarts, and actions such as opening menus or uploading images. It is a case-specific interface, not a public general-purpose verifier. The transferable choice is to make the behavior being changed observable and operable. For a stateful animation, logged coordinates might expose a jump that an agent cannot see; that particular example was contrived, not a demonstrated repair. Different roles or permission states also need appropriate access, not just one convenient login. [4] [5] [6]

Return failures, repair, and recheck

Give the agent a repeatable project-specific verification command and return the failing assertion, relevant state and diagnostic context, not only “failed.” The agent can then make a targeted change and rerun the check on the new artifact. A diagnostic that links a violated rule to its rationale and intended fix is more useful than relying on the agent to remember a long policy document. [7] [8] [9]

Illustrative example: a ticket check-in refactor accepts a ticket twice. The verifier reports the scenario, the second response and the expected rejection. The agent changes the check-in logic, reruns that scenario and the relevant regression suite, and reports which checks ran. If a scanner or automated reviewer suggests a further fix, that fix changes the artifact too: scan or test it again. A similar ticket-scanning failure and CI repair loop was shown in a demonstration; it does not establish a general repair success rate. A clean scan means no findings from that scanner, not no vulnerabilities. [10] [11] [12]

Use fast, inexpensive checks repeatedly in the edit loop and reserve broader, costly work for a pull request or another appropriate boundary. Mutation testing and agentic QA are proposed outer-loop options, not proven time savings. Some integration checks cannot be moved earlier safely; pushing a check past merge can instead expose the shared branch to the risk it would have caught. Set a retry budget and escalate persistent, contradictory or inconclusive failures rather than treating an endless retry as completion. [13] [14] [15]

Make workflow transitions enforce checks

A completion hook can launch configured checks whenever a session finishes; a pre-commit hook gives early feedback; shared CI reruns required tasks even when local hooks were skipped. An explicit state machine can require implementation → verification → review, return review findings to implementation, and allow closure only after the revised work is accepted. These controls make invocation and sequencing less dependent on an agent remembering instructions. [16] [17] [18]

Separate three claims: the check was invoked, it reported a pass, and the desired behavior is actually correct. Deterministic scheduling can invoke a nondeterministic model judge; neither reliable invocation nor a green result makes that judgment correct. Select and assess the underlying checks separately: see Tests, oracles and verifier validity and Testing product behavior and visual regressions. [19]

Separate shared enforcement from project policy

A common runner can accept project-specific rules while the platform requires organization-wide security and compliance checks. Teams define their domain rules with explicit scope, severity, examples and actions: a pricing-file change might trigger review of customer-facing fees, while a low-risk style preference remains advisory. A demonstrated workshop treats severity as an organizational policy decision, not an intrinsic property of a rule. [20] [21] [22] [23]

Have the agent identify applicable rules and explain its selection; have a human review inferred conventions before making them mandatory. Crucially, a deterministic block on a detected serious finding does not guarantee that an upstream selector noticed the relevant rule. Check selection coverage as well as enforcement. The organizational case describes the intended guarantee but does not disclose its full configuration or coverage audit. [24] [25] [26]

Plan reviewable slices and preserve state

For substantial work, agree on product behavior, component contracts and enough program structure to expose important assumptions. Sequence cross-system work into vertical slices: each has defined inputs, outputs and an observable check, and is validated before dependent phases rely on it. A practical size heuristic is whether its change can be reviewed in one sitting, not an arbitrary line limit. Splitting also creates interface and coordination costs; large changes can be reasonable when properly planned and tested. A speaker reports reviewers sometimes reimplemented oversized agent submissions rather than trusting them, an observed anti-pattern without measured frequency. [27] [28] [29] [30] [31]

Planning detail is conditional. One team’s later approach kept product direction high-level and negotiated concrete features and tests nearer implementation, avoiding a wrong early technical decision cascading through every sprint. Earlier harnesses needed more explicit feature decomposition. Specify stable constraints early, but bind uncertain implementation details when there is evidence to decide; neither maximal nor minimal planning is a universal rule. [32]

A fresh worker also needs durable state. One earlier harness initialized a feature list, progress file, repository and startup script; each worker oriented itself, smoke-tested the environment, implemented and checked one failing feature, then committed and updated progress. Record where features live and how to build and test so later workers can resume rather than trust conversation memory. This was one harness design, not proof that any particular file format prevents lost state. [33] [34]

Before scaling parallel agents, make the repository usable: reproducible setup, meaningful tests, documentation and linting provide feedback that an agent can actually run. The reported association between readiness and adoption success is observational, not proof that these practices alone cause it. [35]

Isolate parallel work and validate the landing combination

Separate checkouts or Git worktrees reduce direct interference when concurrent agents stay within their assigned working directories. Check both that intended work appeared in its assigned checkout and that forbidden changes did not appear in the primary checkout: either check alone can miss a failure. Worktrees are not security sandboxes. They also do not isolate a shared test database: parallel tests can contaminate one another and become intermittent unless test state is separated or access guarded. A reported database incident illustrates this risk, not a general accuracy rate for automated review. [36] [37] [38]

Two branches can each pass against the same base and still fail together. A merge queue reconciles the intended landing order and tests the candidate combination against the current shared state before admitting it. One described infrastructure tests likely combinations in parallel and removes a predicted breaking change. This is integration protection against covered interactions, not a formal serializability proof or a detector for every semantic conflict. [39] [40]

Agent navigation across several repositories does not eliminate the cost of cloning, provisioning a sandbox, end-to-end testing and deploying their combined changes. Include those costs when choosing boundaries. One team chose a monorepo; isolating a component without a full consolidation can also be appropriate. [41]

Finally, revisit requirements and gates as models, tools and dependencies change. Check whether assumed capabilities are actually released and whether a previously useful guardrail still catches the relevant failure. A single-team retrospective reports that its verification practices evolved; it is not a complete universal framework. [42]
