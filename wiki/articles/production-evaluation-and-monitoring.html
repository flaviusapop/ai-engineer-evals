Production evaluation and operation

Monitoring production quality and improvement

Operational measurement and uncertainty, not human decision rights. Owns quality signals, test evolution, risk and task outcomes; execution traces and platform plumbing are covered elsewhere. Observability, discovery and continuous evaluation rather than offline release authorization.

On this page

  • Choose what to score and how much to observe
  • Interpret changes, not just dashboard movement
  • Use feedback to discover what the metrics miss
  • Keep evaluation aligned with the product

A production agent can pass a fixed evaluation and still fail a user: the request distribution changes, a provider changes a model or tool, and the agent takes a path the test set never anticipated. Monitor the live workflow as well as the release candidate. The aim is not one all-purpose quality score, but evidence that connects user goals, observable outcomes and the behavior that produced them. [1] [2]

Define success at the workflow boundary

Before deployment, decide what improvement would matter to users or the organization and what evidence would show it. A deployed agent, a large number of calls or low token use is not itself business value. For a support agent, for example, define the intended resolution and separately observe whether users got it, what it cost, and whether they had to escalate. The right measures depend on the job; no single ROI formula follows from the principle. [3]

A successful HTTP response or tool call establishes an operational event, not a useful answer or correct action. Evaluate planning, tool choice, execution and recovery as well as the final message and resulting state. In a constructed stock-sale demonstration, the user requested a dollar amount, but the agent supplied that number as a share quantity; the broker successfully executed the wrong payload. The lesson is to compare the action and result with the user's intent, not require every successful run to match one prescribed trace. [4] [5] [6]

Likewise, individual tool competence is not completion of a cross-system job. An onboarding workflow might create accounts, arrange introductions and order equipment, yet fail because a handoff was missed. Measure the state of the entire job, including unfinished dependencies, rather than counting successful calls. For methods of establishing outcomes, see Verifying agent outcomes and diagnosing behavior. [7]

For a transactional workflow, record eventual completion and the cost of all attempts, including failed ones, per completed transaction. Partial activity may have little value for that particular business process; that need not hold for exploratory research. Retrying can improve eventual completion but costs more and may repeat side effects. State whether a budget counts total attempts or additional retries, and do not assume failures are independent or retries safe. One source's approximately 94% example is ambiguous about attempts versus retries, so it is not a general reliability prediction. [8] [9]

Choose what to score and how much to observe

Keep latency, errors and cost, then add application-specific semantic measures such as incomplete resolution, incorrect actions, or refusal when assistance was appropriate. Run developed evaluators on incoming production traces continuously, retain their assessments alongside execution evidence, and investigate changes; a prompt fix does not end monitoring. Semantic classifiers are measurements requiring validation, not ground truth. A successful infrastructure dashboard and a passing offline set cannot substitute for this live view. [10] [11] [1]

Match scoring scope to the question. A tool-argument check may need a single span; whether a plan recovered from a failure needs the full trace; whether all questions were answered may require a grouped conversation. Preserve relationship identifiers, timestamps and version metadata so these pieces can be joined. Score a long interaction when enough context is available; an arbitrary timeout or a single turn can miss its outcome. The demonstration's timeout is not a universal default. [12] [13]

Track the proportion of eligible traffic actually scored, broken down by version and filter, alongside the quality rate. A missing score is not a pass. A workshop demonstrated a seeded coverage gap, but supplied no denominator from which to estimate its production impact. Coverage also does not prove that the scored traffic is representative or that the evaluator is accurate. [14]

Sampling and evaluation investment depend on risk, traffic and cost. A low-consequence product might learn quickly from live iteration; a catastrophic error warrants stronger predeployment checks and more cautious exposure even if the failure appears rare. Small populations may not support ordinary A/B testing, and uncertain rankings can justify collecting more evidence rather than selecting a winner. There is no universal sampling rate or safety threshold here. [15] [16] [17]

Interpret changes, not just dashboard movement

Compare outcomes over time with configuration and population changes in view. In one discussion of a daily tracker using 50 software tasks per run, a proposed downward trend was contested; confidence intervals and the asserted moving-average plot were unavailable, and model versions changed even though the harness stayed fixed. Smoothing can help show a pattern but does not establish a decline or its cause. [18]

For a model replacement, shadow both candidate and incumbent on the same inputs and repeat runs. Compare incumbent against itself, candidate against itself, and candidate against incumbent. This separates ordinary output variability from cross-version differences: disagreement is not an accuracy estimate, and the source supplies no universal repeat count or sample size. Examine disagreements against actual task outcomes before calling them regressions. [19]

When a candidate is ready for live exposure, tag traces with the experiment and configuration and compare an exposed cohort with a suitable control on user-facing issues as well as latency and cost. Segment outcomes by relevant user intent, device or other context: an aggregate can conceal a concentrated failure. A spike in frustration is a useful investigation lead even before results are conclusive; it is not automatically a causal release effect. Group sizes, sampling, assignment and uncertainty matter, particularly for small slices. [20] [21] [22]

Move between the distribution and individual trajectories. Measure a recurring failure pattern over multiple cases instead of rewriting a prompt after one stochastic run; then inspect paired task outcomes and traces to explain why a candidate routed or acted differently. A trace records the workflow and spans record individual model or tool steps. Check which tools were available, called and actually used, not just a static diff or a plausible final answer. One path can expose a mechanism without establishing its prevalence or cause across all traffic. [23] [24] [25] [26]

Use feedback to discover what the metrics miss

A whole-session outcome asks whether the user's needs were resolved, which differs from a correct-looking tool call. Ratings and direct feedback add subjective experience, but respondents select themselves: satisfaction, factual correctness and completion are distinct. Cheap indicators such as all-caps messages or inferred gratitude can point reviewers toward candidate failures or adoption patterns; neither establishes a user's mental state or the answer's correctness. Validate the interpretation rather than treating the proxy as a label. [27] [28] [29] [30]

Known checks scale, but discovery also needs customer conversations, open-ended human review and inspection of unusual trace clusters. A cluster is a lead, not a verified failure category or a guarantee that all categories were found. Small, messy deployment anecdotes can reveal possible mechanisms worth testing; they cannot establish population rates or rank models. When a reviewed case warrants a maintained fixture, follow Build and maintain production-grounded evaluation sets rather than assuming every observation belongs in a regression set. [31] [32]

An agent can also report friction through a simple tool: missing capabilities, repeated tool failures or workarounds. In a small workshop, neutral creator-feedback framing elicited observations more readily than framing the report as an admission of bad behavior. Reporting frequency depends on the prompt and reports are selective self-assessments; independent traces and human checks remain necessary. [33] [34]

For an investigation agent, make relevant trace groups and associated evidence available through programmatic interfaces, not only a human dashboard. Package the specific observations needed for a question rather than dumping all telemetry into its context. This is an architecture recommendation, not evidence that automated diagnosis or repair is safe or correct. [35] [36]

Keep evaluation aligned with the product

Retain stable regression checks while revisiting coverage as model versions, provider tools, prices, latency, user language and workflows change. A provider integration can change outside the application's control; a test distribution that represented early adopters may miss later usage. The proposed always-on, agent-maintained evaluation architecture is unfinished, not a demonstrated replacement for human maintenance. [37] [38] [39]

Simulation can screen many candidates before scarce production experiments, using metrics aligned with the actual job. In one customer/vendor account, simulated interactions reportedly caught regressions and helped screen open-source models, while live A/B tests continued. The account does not quantify the failures missed or candidates wrongly rejected by the simulator. Validate the simulator against real usage and confirm selected changes in production; offline and shadow gains alone do not establish live product value. [40] [41] [42] See Building and validating simulated agent worlds for simulation fidelity.

Some product outcomes require qualitative domain review. A visual model's default style when a user gives no direction is a product choice, not an objective optimum; users should still be able to steer it with instructions or references. In a vendor panel, expert testers noticed blurred grass and recurring unwanted rings that broad scores could miss; the proposed explanation for the rings was not established. Combine scaled evaluation with trusted reviewers testing their real workflows, and do not infer an optimal aesthetic policy from this anecdote. [43] [44] [45]

Finally, if other agents are users of the product, test whether they can operate its interfaces and complete their tasks, separately from testing agents that help build the product. The suggested business benefit is a hypothesis, not a measured result. [46]
