Efficiency and performance

Designing efficient agent workflows

Covers delivery loops and replay, not retrieval context or production serving. Trajectory and development workflow design, not evaluator scheduling.

Download Markdown

On this page

  • Extract and maintain reusable production procedures
  • Use captured model outputs in deterministic regression tests
  • Find the delivery bottleneck
  • Budget verification and repair
  • Measure complete trajectories
  • Allocate work by structure and dependency
  • Enforce limits, not just intentions

An agent can produce a correct answer and still make the workflow slower or more expensive: it may repeat a tool call, wait on a shared test suite, or produce changes faster than people can review them. Design for accepted work per unit of time and cost, not just generation speed. The useful question is where flexibility is necessary, where work can be reused, and what actually limits delivery.

Extract and maintain reusable production procedures

Begin with the desired outcome and allow flexible exploration where the path is uncertain. When similar requests recur, inspect successful traces for stable mechanics that can become parameterized code. In an insurance-portal architecture, a reusable authentication component prepares a browser, an agent handles variable navigation, and one tool bundles downloading a document and transferring it to the runtime. An SOP can guide the flexible stage without pretending the SOP itself is executable. The proposal reduces model decisions, but does not measure savings or reliability; its authentication and session-security details are not specified. [1] [2] [3] [4]

Run the extracted procedure on later requests only after checking that parameters, preconditions and outcomes preserve the user's constraints. Detect failures or drift and fall back to adaptive execution or repair. A schedule-lookup demonstration saved actions as code and changed the day parameter; replay hit a hiccup and fell back to a vision-language agent. This hybrid is experimental, not a guarantee of reliable replay. Browser shortcuts such as encoded URLs can bypass fragile UI interactions, but selected demos do not prove that every site constraint is preserved. [5] [6]

Compare the initial discovery bill and ongoing maintenance against expected reuse, rather than assuming the cheaper path pays off on its first use. Reactive repair avoids routine probe costs but lets a user encounter stale behavior; scheduled sample runs spend resources to find drift earlier. The proposed repair approach was still a working theory, not a demonstrated universal maintenance policy. Security boundaries for the components remain a separate concern: see Agent Authority, Isolation and Runtime Controls. [7] [8]

Use captured model outputs in deterministic regression tests

Production procedure reuse runs extracted actions on a new request. A different kind of replay tests application code against already observed model decisions: capture the model outputs and context, substitute them into the test, and run the deterministic nodes to see whether a code change handles that known case correctly. To avoid fresh inference, stub every relevant model node. A demonstrated test stubbed the planner but left a later language model active; it was not itself a zero-model-call run. Even fully stubbed tests still use infrastructure and may miss hidden external dependencies. They cannot tell you how a changed model behaves on new inputs, so retain live behavioral tests. [9]

Find the delivery bottleneck

Map elapsed time from specification through generation, validation, review and release. Faster coding helps little if review or the release queue is saturated. One speaker's hypothetical monthly release growing from 20 to 200 pull requests illustrates the queue problem, not a measured result. Another reports roughly tenfold faster builds after a tool change; that is a build-time observation, not a tenfold improvement in total delivery. Failed centralized checks can also impose long waits and interrupt human flow. [10] [11] [12]

Use fast feedback suited to the current task: for example, browser iteration for UI changes or a coverage- and change-selected test subset during editing. Keep broader final CI checks rather than treating a locally green subset as acceptance. Deep security scans may warrant a different cadence: one vendor demo described a roughly hour-long scan, but one project does not establish an optimal schedule or scaling rule. [13] [14]

Budget verification and repair

Separate uncertainty about how to do a task from uncertainty about what counts as right. A task with a variable path and a repeatable, inexpensive check is a promising agent candidate; if checking effectively requires redoing the work, automation may not save effort. This is a proposed task-selection framework, not a validated complexity classification. Include model and tool costs, checker runs, human review, infrastructure and maintenance. False positives matter too: an unnecessary automated fix costs effort and can introduce another defect. [15] [16] [17] [18] [19]

Checks may make a failed first attempt repairable, but neither correctness nor lower accepted-work cost follows automatically. The idea that stronger harnesses enable cheaper models is a hypothesis to test on the actual workload. A selected game-making demonstration reported about $200 and six hours for a successful harness run, without a controlled cost comparison. An under-tested recruiting integration reportedly produced repeated formatting errors and costly workarounds; the account supplies no retry counts or measured savings. Inspect such loops and stop unproductive repair, rather than judging only the final artifact. [20] [21] [22]

Measure complete trajectories

Record completion against the original requirements, calls and retries, tokens, elapsed time and timeouts alongside answer quality. A correct account-balance answer can hide three database calls; some repeated calls may be justified, so investigate rather than treating minimum call count as the objective. A minimal file-creation probe reportedly exposed a 70-fold token difference between unnamed models in one harness; absent full run conditions, this is a reason to probe your own setup, not a model ranking. [23] [24]

Per-step accuracy is also not the same as end-to-end completion. A thought experiment with 100 required steps at 99% independent success gives roughly 37% success without recovery; correlated failures or recovery change the result. It is not a measured browser-agent reliability figure. [25]

Allocate work by structure and dependency

Use a script for a fixed procedure; use a model where interpretation or selection is genuinely uncertain. A financial example has the model select what to calculate while code extracts inputs and computes the result. Deterministic arithmetic does not validate the chosen sources, definitions or plan. Similarly, selecting among approved responses may be a classification problem rather than open-ended generation, but the classifier itself still needs evaluation. Generated code can batch structured exploration; constrain its effects because flexible code can bypass intended mutation paths or lineage. [26] [27] [28] [29] [30]

Parallelize independent work, not dependent decisions. In a travel example, flight and hotel searches can run together, but a budget check needs both prices and an activity search needs the remaining budget. The application must dispatch calls concurrently for the suggested parallelism to matter. Isolate standardized evaluation environments before running them in parallel, and account for capacity and orchestration. Serialize conflicting writes where necessary; one team's account favored parallel read-only research but serial feature changes after simultaneous workers produced conflicts. [31] [32] [33]

A different, speculative proposal duplicates an implementation across several candidate repository bases, hoping one will fit a rapidly moving shared state. Unlike independent reads, this spends extra compute on alternatives and still needs reconciliation and validation. No measured benefit or scheduling policy was supplied. [34]

Enforce limits, not just intentions

Set separate runtime limits for steps inside an attempt, retries across attempts, elapsed time and total spending. A prompt saying “search sparingly” or an iteration limit is not a hard session-wide monetary cap. Inspect repeated searches for genuinely new evidence; one team prompted the agent before a sixth call to reconsider, but that instruction was not an enforced cap. For automated test-and-repair, protect test integrity and stop when the budget is exhausted rather than letting a loop weaken tests to pass. Choose timeouts for the actual startup and execution environment, not a demo's numbers. [35] [36] [37] [38] [39]

For the distinct problem of staging evaluation and monitoring budgets, see Budgeting evaluation and monitoring.
