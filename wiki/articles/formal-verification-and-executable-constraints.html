Verification and assurance

Formal verification and executable constraints

Owns deductive guarantees and executable structural constraints, not the organization’s process for choosing review policies.

Download Markdown

On this page

  • Tests, specifications and proofs
  • How a proof is constructed and what it covers
  • Encode repeatable constraints in the development path
  • Put the enforcement point where effects happen

A green check has a scope: it says that a particular mechanism accepted a particular artifact under particular conditions. A test suite, a compiler, a runtime validator and a proof checker establish different things. The engineering task is to choose the right claim for each boundary, then verify the connections between them—not call the whole system correct because one component passed.

Tests, specifications and proofs

A failed test can expose a counterexample; a passing suite establishes behavior on the cases it exercises. Exhaustive testing can cover all cases in a genuinely bounded domain, but most useful suites sample a much larger space. A valid formal proof instead establishes the stated property for the inputs and conditions covered by its assumptions. Neither a proof nor a test suite establishes requirements that nobody specified. A reported TypeScript-Go scorer, for example, assigns full credit for passing its repository tests and zero for failing; that is an explicit oracle, not proof beyond the suite, and the source leaves the exact localization-versus-repair output contract unclear. [1] [2] [3]

Start formalization with a critical property and make the preconditions and desired result explicit. A human must review the formal statement against the actual intent, including when an AI translated prose into the specification. Checking representative inputs can expose misunderstandings, but examples cannot prove the specification captures every requirement. Keep that specification as a control artifact while implementing; when implementation reveals an omitted case or a product decision changes, update the specification and recheck the proof rather than preserving a formally correct answer to an obsolete question. Capture relevant decisions made during implementation, not just the initial ticket. [4] [5] [6] [7]

How a proof is constructed and what it covers

In an interactive Lean workflow, tactics search for a proof, potentially backtracking and splitting a theorem into helper lemmas. An agent may propose tactics, but its confidence and failed attempts are not the evidence: the trusted kernel checks the resulting proof object. Exporting proofs for independent checking reduces reliance on the search procedure, while still relying on the statement and checker. A speaker describes an AI-assisted compression round-trip proof built from many lemmas, reportedly about a week of work and 32,000 proof lines; the artifacts were not independently inspected in the supplied account. [8] [9] [10]

Different engines check different representations. The described Verus route places requires and ensures contracts alongside Rust code and uses solver-backed static obligations; these are not runtime assertions. Interactive Lean tactics and SMT solvers offer different proof workflows, and neither guarantees automatic success for every program. Ask what code or model is actually checked, how it was translated, and what tools and assumptions are trusted. The proposed Strata design lowers language-specific dialects into a common Lean-based intermediate representation and dispatches to proof, SMT or model-checking backends. It is work in progress, not evidence that every language is supported or that lowering is automatically trustworthy. [11] [12] [13]

A proof of a model is not automatically a proof of a separate deployed implementation. In the speaker-reported Cedar example, a Lean functional specification and Rust implementation are compared on the same random inputs, with roughly 100 million differential tests nightly and agreement required for release. That is a substantial sampled bridge between model and implementation, not an all-input refinement proof of Rust or verified deployment. The figures and release policy are reported rather than independently audited here. [14]

Encode repeatable constraints in the development path

Not every important rule needs a theorem prover. Mine repeated review feedback for conditions that can be checked reliably, turn those into maintained tests, lint rules or structural boundaries, and leave qualitative judgment to review. This takes upfront work; a proposed review-feedback registry is not evidence of a measured reduction in defects. For example, one team describes separating layers, linting imports, returning plain data rather than ORM objects, and disallowing database access from rendering templates. These restrictions target a route to accidental extra queries; they do not prove every possible query antipattern absent. In a separate invoice workflow, missing tax extraction triggers a retry and a negative value goes to a human—local business rules, not universal tax law. [15] [16] [17] [18]

Types can make some invalid states difficult or impossible to express within the checked boundary. An optional value makes absence explicit, requiring code to deal with it before accessing the value; the application still has to choose the right missing-value behavior. Compiler diagnostics can also reject covered concurrency or memory mistakes before execution and provide repair feedback. In one narrated example, a shared counter captured by threads is rejected because its representation is not suitable for that use. Strict-mode settings alone are insufficient if escape hatches leave unwanted states expressible, and compilation is not general semantic correctness. Weigh the whole write-check-repair loop, rather than only how quickly a model produces a first draft. [19] [20] [21] [22]

A mature codebase can add narrow checks without a wholesale rewrite. Sentry describes rules requiring useful endpoint response types and schema decorators, then checking that produced types agree with OpenAPI declarations. This catches a specific form of contract drift, not every mismatch a client may encounter. [23]

For legacy violations, record a versioned, deterministically ordered baseline and reject newly introduced violations while migrating old ones. In a described RPC migration, a scan identifies existing unmigrated procedures and prevents new baseline violations; this ratchet makes progress possible without claiming all existing code is clean. Likewise, a demonstrated analysis hook distinguished a newly fixed finding from a separate preexisting issue. [24] [25]

Put the enforcement point where effects happen

A model can reason flexibly while the application restricts what actually changes. In Watershed's described graph-editing workflow, typed SDK primitives distinguish editable fields from values derived from other fields and produce structured edits. But an SDK and the agent's declaration of completion are guidance, not the final authority. A system-controlled executor lints generated code, checks overlapping or dependent edits, runs the code, validates resulting artifacts and constructs a review artifact; failures can return actionable feedback. This constrains the described commit process, not whether the user's sustainability judgment is substantively correct. The account does not establish that all alternate commit paths or isolation risks are excluded. [26] [27] [28] [29]

A similar division applies to calculation: a financial-research model can plan which filings or restatements are needed, while predetermined human-written software retrieves facts and performs arithmetic. Deterministic calculation makes the operation inspectable and repeatable for given inputs; it does not validate the inputs or the chosen financial interpretation. This architecture is vendor-described, not independently audited. [30]

For failures that escape a local boundary, see diagnosing failures across system boundaries.
