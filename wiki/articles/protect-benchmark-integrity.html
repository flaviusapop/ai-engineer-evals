Agent evaluations

Protect benchmark integrity

Covers leakage and scoring exploits; not general simulator validity.

Download Markdown

On this page

  • Close unintended answer channels
  • Protect the grading boundary
  • Test the incentives, not only the defenses

A high benchmark score is meaningful only relative to what the agent could see, change and exploit. A system that finds a published answer may solve a practical problem, but it has not demonstrated the same capability as one that independently derives the answer. A system that changes its grader has demonstrated neither. State the intended capability before deciding which access is appropriate.

Close unintended answer channels

A checkout at an old commit is not necessarily a historical environment: later solution commits may still be reachable through repository objects or branches. One speaker reported an agent finding and copying a future solution patch; another demonstration openly showed an agent copying a neighboring pre-solved implementation. The latter can illustrate an assisted workflow, but not clean independent repair from the original code. Inspect adjacent files, refs, history, task instructions and network access for such shortcuts. Original tasks can reduce exposure to public solutions without eliminating every contamination route. [1] [2] [3]

Consider equivalent capabilities, not just tool names. In a reported sequence, after an agent's web tool was blocked, it used shell curl to access the same issue discussion. Restricting one interface is not the same as restricting the underlying network route. Review trajectories and apply access controls to the actual capabilities; the described post-processing and trace inspection are not a complete prevention guarantee. Even a point-in-time search snapshot does not remove future knowledge from model weights. [4] [5]

Controls change the test. Git history and internet access may be normal, valuable engineering tools, and there is disagreement about calling use of supplied history cheating. If the construct is independent solution of an unseen problem, answer access invalidates that interpretation; if it is real-world completion, retrieval may be legitimate. One team reports removing history and allowlisting network destinations for public evaluations, while describing private held-out real tasks as a way to retain more realistic access. Its score changes were not quantified and the private holdout was not independently audited. Similarly, test locations and required interfaces can be legitimate requirements rather than inherently leaky hints. Document the choice and its trade-off. [6] [7] [8] [9]

Protect the grading boundary

Separate instructions and permitted work from reference answers, tests, grading code and credentials. A described coding-benchmark walkthrough saves the implementation patch, reverts agent changes to tests, applies hidden reference tests, and runs both old and new tests. Another described setup mounts verifiers only after the agent finishes. These measures reduce opportunities to weaken checks or inspect scoring, but hidden files alone are not a security boundary and neither example proves a complete defense. [10] [11] [12]

Isolate the trusted grader from the agent's writable runtime and keep unrelated model credentials out of reach. An audit speaker reports cases of agents changing writable grading scripts and another case of an agent using another model's exposed key; the latter breaks attribution even if the answer is right. These incidents lack identified cases and prevalence estimates. Log calls and submissions so an investigation can distinguish answer lookup, suspicious probing, an attempted bypass and an exploit that actually receives reward. A benchmark speaker reported suspicious activity, submitted bypasses and zero rewarded exploits as distinct outcomes. Those speaker-reported observations do not prove universal robustness. [13] [14] [15]

Test the incentives, not only the defenses

Ask whether a high score requires the intended work. One speaker reports that, in some existing data-science benchmarks, 20–50% of tasks could be solved with the underlying data withheld. That audit is a warning about those benchmarks, not a prevalence estimate for all data science. If the data are supposed to be essential, success without them suggests the task or grader rewards prior knowledge or a shortcut instead. [16]

In a coffee-order leaderboard discussion, participants noted that a deterministic parser placed near the server could exploit a single-order latency objective. Such specialization might be useful for that particular service, but a fast score alone would not establish broad interactive-agent competence. Inspect the objective and compare the rewarded behavior with the actual use case. [17]

Integrity is not validity. Preventing access to answers and tampering does not show that tasks are representative, reference answers correct, or tests sensitive to real failures. An isolated grader can faithfully enforce the wrong requirement. See Tests, oracles and verifier validity for validating checks and Choosing and designing agent benchmarks for task selection; protect repeated-use and historical holdouts separately in Protect holdouts and historical evidence.
