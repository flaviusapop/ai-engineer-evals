Tasks, datasets and evidence

Specify and audit meaningful benchmark tasks

Task-level construct and verifier validity rather than population coverage.

Download Markdown

On this page

  • Construct executable tasks and matching checks
  • Specify the objective without prescribing every path
  • Audit the task before interpreting failures
  • Make the environment and evidence matter
  • Renew or shorten tests without changing the question unnoticed
  • Inspect incentives in the tasks and the score

A benchmark task is a claim about what an agent should be able to do under particular conditions. A prompt alone is not enough: the agent needs a usable starting situation, a goal and a way to observe completion. Even a perfectly packaged task can be misleading if its answer is ambiguous, its checks reward the wrong thing or its inputs do not require the claimed capability.

Construct executable tasks and matching checks

Package each task with its instruction, prepared initial state and execution environment, required data and tools, a verifier, and a stopping condition. Separate the task from the harness that runs the agent and the runtime that executes it; document which layer supplies tools, prompts and skills because that division depends on the application. A common format can help others run and extend tasks, but portability, usability and compatibility are not evidence of validity or secure isolation. A harness must actually support the task's required capabilities. [1] [2] [3] [4]

For a repository issue, preserve the issue, runnable dependencies and checks: fail-to-pass tests should fail before a fix and pass after it, while regression tests should keep passing. A test derived from the eventual fix is useful supervision, but may be flawed or demand a solution-specific detail. Another construction starts from a completed pull request, removes selected code and asks the agent to recover a reachable endpoint. Reachability does not make the historical implementation uniquely correct. [5] [6]

Parameterized tasks need matching state and checks, not just varied wording. In a proposed transfer task, the recipient and amount are instantiated together with mock data, initial interface state and a corresponding verifier; broken combinations must be rejected. The source describes the architecture, not the rejection criteria or verifier error rate. Likewise, a project benchmark may include external APIs, whose availability, state and cost are not automatically frozen by packaging; a shared GUI authoring interface does not prove identical semantics across platforms. [7] [8] [9]

A compatible configurable model endpoint can sometimes let an existing harness send requests through a translating interception layer, preserving ordinary harness code while collecting sampling information. This is conditional on endpoint and protocol support, not a solution for arbitrary closed harnesses. For comparison design see Comparing agents without confounding the result; for validation of the checks themselves see Tests, oracles and verifier validity. [10]

Specify the objective without prescribing every path

Describe the user goal, starting conditions, desired behavior and genuine hard constraints. An expected result might be a correct final state, appropriate deferral, or a required tool call and arguments when that behavior itself matters. Avoid treating a particular sequence as mandatory merely because it was the author's solution: a harness upgrade or a scientifically sound alternative may achieve the objective differently. High-level tasks leave room for exploration, but can need hints and richer grading to remain solvable and fair. [11] [12] [13] [14] [15]

For example, scientific analysis can admit multiple valid methods. Specify conditions that should hold across those methods rather than silently assuming one canonical path. A deterministic check can still encode an unjustified scientific choice. If correctness, useful insight and efficiency are separate goals, specify them separately: one demonstration used two model judges and a six-call rule, but did not validate the interestingness judge or establish six calls as a general limit. [16] [17]

Audit the task before interpreting failures

Read the instructions, supplied artifacts, expected answer and actual checks together. Ask independent experts to attempt the task and cross-review the resulting solutions; use an adjudicator and revision when they disagree. Run agents too, because attempted execution can reveal broken environments or hidden task defects. One coding-task curation account selected extra candidates to replace defective ones and manually checked final tasks; its reported extra sample was ten percent, not a universal reserve. [18] [19]

In one scientific example, human attempts exposed unresolved choices about gene groups, normalization, neighborhood radius and aggregation. A disagreement with the expected number may reflect the task's ambiguity rather than poor reasoning. Decide whether a choice is essential and specify it, or accept justified alternatives; revisit arbitrary inherited thresholds before turning them into hard failures. Scientist cross-grading was the team's available proxy where no canonical answer existed, not proof of truth: no inter-rater statistic or detailed protocol was reported. [20] [21] [22]

Also look for contradictory instructions and checks that omit a requested outcome. A significantly negative item-discrimination estimate—stronger models on the fitted scale tending to fail an item—is a reason to inspect its wording and gold answer, not automatic proof the item is wrong. One demonstration flagged an answer that counted crew when the question asked for passengers; another model's agreement with the criticism is not independent verification. [23] [24]

Make the environment and evidence matter

The files, tool behavior and expected rubric must agree with one another and plausibly resemble the conditions the task claims to test. An agent should not be penalized for following its supplied evidence when the gold answer contradicts that evidence. Obvious placeholders can also alter how the agent behaves. Synthetic material is not inherently invalid, but synthesis and quality control require care. This is a task-fidelity question, distinct from whether a collection has representative sampling proportions. [25] [26] See Design evaluation distributions for decisions for the latter.

Test whether the claimed evidence is actually needed. A model might answer a public-data question from memory without using the supplied source, or answer a purported visual question from text and general knowledge without inspecting image detail. Try removing or changing the evidence and inspect whether the answer should change; for a data-analysis task, ask whether its conclusion genuinely depends on the specific supplied data. The visual-source warning is a speaker's argument, not a reported image-removal experiment or estimate of how many items have shortcuts. [27] [28] [29]

Match fixture size and contents to the behavior under test. A small subset may suffice for a narrow correctness question; pagination or full-database behavior needs enough records to exercise it. The full-database suggestion in the cited case was prospective, not a completed load study. For design-to-code work, the needed fixture is a paired design and implementation: one team created toy repositories because open code paired with design files was scarce in its setting. [30] [31]

Renew or shorten tests without changing the question unnoticed

When results cluster near the ceiling, inspect both task difficulty and grading strictness. Consider extending the test if it no longer distinguishes the candidates, but keep essential easy and safety checks where they serve a different purpose. High scores alone do not prove a bad evaluator, and a suggested ninety-percent signal is not a universal retirement threshold. In one word-inclusion experiment, tested models reached the original 500-word ceiling, so the author extended the lists into the thousands. The extension measures a lexical proxy, not general instruction-following capability. [32] [33] [34]

The extended random word lists sometimes accidentally triggered safety refusals. Those are not the same failure as forgetting an instruction. The author filtered the list for one model; disclose such preprocessing and the altered input distribution when interpreting or comparing results. [35]

Shortening has a different objective from finding defective items. Rank items by estimated discrimination, then check whether a selected subset preserves the original ranking for the models and benchmark in question. In one speaker-reported demonstration, about 97 of 484 items met a 99% ranking-correlation target; the speaker identified GPQA as a counterexample to generalizing the approach. Preserving that ranking does not establish preservation of absolute scores, safety coverage or other decisions. [36]

Inspect incentives in the tasks and the score

A vendor may have incentives to select impressive hard cases or sell material optimized to its own benchmark. One speaker makes that market critique while having commercial interests of his own; it is not an audited industry-wide finding. Define realism using independent knowledge of the actual work, not solely the seller's assertion. [37] [38]

Finally, enumerate what the score rewards and ignores. In a small acquisition-prediction exercise, correct positive predictions earned a point, false positives lost a point, and misses and passes had no effect. That objective encourages a different decision tradeoff from one that penalizes missed acquisitions; a high score does not establish investment performance. Before adopting any score, decide whether its outcome weights reflect the decision you intend to make. [39]
