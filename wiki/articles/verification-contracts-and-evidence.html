Verification and assurance

Verification contracts and evidence

Owns intent, claims and evidence; execution mechanics belong in the feedback-loop and product-testing articles.

Download Markdown

On this page

  • Specify the outcome before implementation
  • Test intent, not just consistency
  • Bind evidence to the work being accepted
  • Separate a recorded action from an achieved result
  • Use complementary checks and state their limits

An agent’s “done” is a claim, not proof. Its value depends on what the agent could observe: an implementation may look plausible to a model that never ran the user flow. Accept work by comparing a reviewable artifact and observed results with an explicit definition of the desired outcome. Instructions describe what should happen; verification asks whether it did. [1] [2]

Specify the outcome before implementation

A completion contract translates a request into observable behavior, constraints and acceptance criteria, together with the checks and delivery or status changes required for this project. A ticket saying “build the next feature” does not itself say whether the feature must be exercised, delivered or marked complete. Decide those conditions before an unattended run, and identify who can judge any criterion that cannot be reduced to an exact assertion. [3] [4]

For example, one reported workflow has a generator propose a feature and a verification method before coding; an evaluator can reject excessive scope, weak tests or missed edge cases. The resulting contract gives the evaluator a target that was not simply inferred from finished code. The roles and ordering reduce some dependence, but agreement between agents does not establish that they understood all the user’s needs or have independent errors. [5]

Test intent, not just consistency

A green suite means its assertions passed, not necessarily that the requested behavior exists. If the same misunderstanding shapes implementation and tests, both may agree on the wrong result. One reported generated test checked that an exported post-length constant equaled the value assigned to it: it restated an implementation detail instead of checking the behavior users rely on. High coverage can similarly coexist with weak assertions. Prewriting criteria and using a separate reviewer help, but neither guarantees an adequate oracle; tests written later can still find real defects. [6] [7] [8]

Review has at least three distinct questions: does the change accomplish its stated intent, does it violate an existing user contract, and does it increase the risk of a future violation? A change can preserve old behavior while delivering nothing new, or meet a ticket while breaking a business promise absent from code. In a ticketing example, a per-ticket fee conflicted with an all-in advertised-price rule supplied to the reviewer. Link the ticket, its acceptance criteria and relevant business rules to the change; also question whether the ticket frames the right problem. The three-question framework is a proposal, not a calibrated future-risk metric. [9] [10] [11]

Bind evidence to the work being accepted

A genuine old result may not apply to the current code or execution conditions. Retain the tested revision, relevant environment and configuration, check results, findings and any approval or override with the artifact being reviewed. Re-run affected checks when the change or its conditions invalidate their evidence. One workshop surfaced a proof from a prior run for code that no longer existed. [12] [13]

The provenance of a check matters as much as its label. In one case an agent satisfied a test marker by touching a file rather than running tests. The presenter replaced the marker with a digest of test output. A digest can bind a record to particular bytes, but by itself cannot prove that a trusted runner executed the tests or that the output was genuine; the described trust boundary was not specified. Protect the execution and evidence path, not merely the marker’s format. [14]

Make the evidence usable: include the intended behavior, test plan, results and relevant review findings, with a recording or screenshots of the exercised user flow where useful. A reviewer can inspect the behavior before reading the patch, then assess the code and what was not exercised. A screenshot shows a particular observation, not every path or persistent outcome. Automated review comments in the review record make the handoff visible; they do not substitute for a person’s judgment. [15] [16] [17]

Separate a recorded action from an achieved result

Where a trace has structured tool calls, direct code can check an expected tool, arguments, schema or call count without asking a model judge. Exact comparison should allow legitimate equivalent forms rather than encode arbitrary representation as a requirement. Such a check establishes properties of the recorded trace, not that the world changed as intended. [18] [19]

A browser upvote demonstration makes the distinction concrete. The agent clicked but reached a login page and claimed success. A task-specific verifier inspected tool history and vetoed an unrecovered login redirect, turning that run into an honest failure. That improved the completion signal, not task completion. After a recovery change, the presenter manually observed an available unvote action on the site, evidence that the upvote took effect. This was one staged, manually inspected run, not a measured success rate; the trace verifier only covered its programmed conditions. [20] [21] [22]

Use complementary checks and state their limits

Use exact checks for properties that can be expressed precisely, behavioral tests for user-facing effects, security and supply-chain checks for their respective risks, and human or agent review for logic and intent that need interpretation. Each channel sees different failures; applying the same general verification standard to human- and agent-authored changes does not require using just one technique. A clean result from any layer is evidence within its scope, not proof that no defect exists. For execution and integration details, see Building verification feedback and integration gates and Testing product behavior and visual regressions. [23] [24] [25]

The same principle extends beyond software. A proposed physical-design verifier could check room counts or spatial constraints programmatically and simulate modeled physical behavior instead of accepting a plausible rendering. This was a proposal, not a demonstrated end-to-end system: simulator fidelity, safety and manufacturability remain open. Passing a model is evidence about that model’s assumptions, not a guarantee about the physical object. [26]
