Efficiency and performance

Managing context, retrieval and cache costs

Covers retrieval and context policies, not tool catalog interfaces or inference cache billing. Covers prefix placement, replica locality and billing rather than general KV sizing. Context, knowledge and retrieval economics, not model-selection economics.

Download Markdown

On this page

  • Select evidence without losing the way back
  • Choose the context policy by workload
  • Budget the retrieval pipeline
  • Reuse prefixes and price the whole run

An agent needs enough evidence to make the right decision, not necessarily every available document. But removing context is not free: search, indexing, summaries, cache misses and repeated retrieval all add work, and a shorter prompt may omit the one fact that changes the answer. Choose a context policy by testing the complete task, not by minimizing tokens in isolation.

Select evidence without losing the way back

Filter, aggregate and deduplicate before sending material to the model: a short answer cannot recover input cost already incurred. For code, an overview of signatures can orient the agent, followed by expansion to the relevant implementation and callers. Remove overlapping retrieved chunks, but retain identifiers or locations so the agent can inspect the original. These are design strategies, not demonstrated guarantees of coding quality. [1] [2] [3]

A diagnostic system illustrates the tradeoff: it clusters exceptions, ranks them by relevance and timing, presents truncated top results and lets the agent request the full log for an exception. The recovery path matters because ranking or truncation can hide the decisive clue; the reported improvement in signal-to-noise was not accompanied by measured diagnostic accuracy. For numerical questions, a query such as SQL aggregation can answer directly rather than paginate every trace into context. Generated redaction or summaries require separate validation; neither is a privacy guarantee. [4] [5]

Keep bulky traces, intermediate results and media in a queryable store, passing references or selected results instead of repeatedly embedding whole payloads. Make retrieval completeness, permissions, retention and read load part of the design: external storage can relocate rather than eliminate cost. Separately referenced images can also avoid base64 text bloat; that example is not a general performance benchmark. [6] [7] [8]

Choose the context policy by workload

Compare full context against retrieval, clearing, summarization and fresh sessions on the same representative tasks. Track answer or action quality, latency, actual charges, retained evidence and replacement work. In a reported literature-review experiment, the relevant corpus fit in the window and memory variants added cost without improving performance; this does not establish that full context wins on larger corpora. Conversely, a local setup with a 32K window could not fit some lessons: a cache discount does not increase physical window capacity. [9] [10]

Clearing a useful tool result may force the agent to retrieve it again. A compact summary saves space but may lose a qualification or drift; a fresh session can also discard useful history. Test the downstream consequences and cost of reconstruction rather than adopting either continual retention or mandatory reset as a rule. Maintain indexes as the underlying corpus changes. See Running and resuming agent sessions for session recovery and compaction in the longer-running workflow. [11] [12] [13]

Budget the retrieval pipeline

Measure query construction, embedding inference, index construction and maintenance, search, reranking and the answer task—not just vector-search latency. Start with an approach appropriate to the corpus: some practitioners favor hybrid lexical and semantic retrieval from the outset, while others start with lexical search and add semantic infrastructure only if it improves a relevant failure. A cross-encoder scores query and candidate together and can improve a shortlist, but doing that for every document increases query-time work. Stop adding stages when the improvement in relevant task outcomes no longer justifies their cost; no universal threshold follows from these examples. [14] [15] [16]

Limit sequential search rounds and, when helpful, search independent aspects in parallel; breadth still consumes resources. One knowledge harness uses bounded rounds and parallel aspects as a design choice, not a proven optimum. Retrieval relevance and fast search are intermediate measures: separately verify whether the final answer uses the right evidence. [17]

Corpus organization also determines search work. A layout arranged by year can make a cross-year question expensive to traverse. Indexing and embeddings move work upfront and require refresh, potentially paying off across repeated queries. Multiple indexes at different chunk scales can find both local details and document-wide context, but use more storage and fusion work; parallelism is an argument for latency, not a measured guarantee in the cited example. [18] [19] [20]

For a recurring hierarchy, an alternative is to give the model a compact description of paths and let code resolve the selected structure to underlying instances. This avoids listing every asset in the prompt only when the hierarchy is repetitive and the index, filters and selected plan are correct. The reported scaling example does not prove a bound for arbitrary graphs; measure total validation work as well as per-query tokens. [21] [22]

When choosing an engine, distinguish the relevance scoring method from the implementation that finds top results. Test representative concurrency, metadata filters and authorization. Filtering after retrieval can remove eligible results from a small candidate set; filtering first can cost speed. Compare recall as well as latency under real load. A vendor's native-filtering claim is not a universal optimum. [23] [24] [25]

Reuse prefixes and price the whole run

A stable shared prefix can avoid repeated prefill computation if the serving system actually retains it. Put shared instructions before changing request content, then compare cold and warm requests. If caches are local to replicas, routing a repeated prefix to a different replica can miss even though the text matches. The cited warm-prefix demonstration lacks enough controls to predict a production speedup; verify cache hits and latency for the actual deployment. [26] [27] [28]

Inference reuse and billing are related but distinct. Calculate charges for cached and uncached input, output, summary calls and any prefix changes, using the provider's actual terms. Compaction can make a shorter history more expensive if it invalidates a cheap cached prefix. In one reported 36-turn configuration, roughly 1.78 million tokens and 97% cached input made retaining history cheapest among the tested strategies. The limited trials and provider-specific pricing do not establish a general break-even. [29] [30]

Whole-response caching is different again: it reuses an answer, not merely computation for a prefix. Consider it for genuinely equivalent requests only when a key accounts for changing context, model or instruction versions, freshness and access permissions. A previously correct answer can be stale or unauthorized for a different user. A claim that much repeated spending is redundant lacks the dataset and method needed to generalize. [31]

Warm development environments and checkpointed histories are also distinct from response caching. Reuse may avoid rebuilding state, but test isolation and invalidation; summaries need factual-retention checks. Availability of provider caching alone does not establish a hit rate or savings. For tool catalogs and progressive disclosure of interfaces rather than general context policy, see Tool interfaces. [32] [33] [34]
