Judges and evaluators

Give judges the evidence and context they need

Evidence access and verification, not judge error-rate estimation.

Download Markdown

On this page

  • Evaluate faithfulness to supplied evidence
  • Verify sources and critic objections
  • Supply policy, case context and qualified behavior signals

A judge can only assess a property for which it receives relevant evidence. A plausible verdict on the wrong trace span, an empty tool result or a stale reference is still a verdict about the wrong input. Treat the judge's data contract as a separate design decision from the rubric and from the question of whether the judge agrees with trusted labels.

From criterion to resolved evaluator inputs

Start with the specific question, then identify the observations needed to answer it. For a final itinerary, the judge needs the user's request and the itinerary; a root span containing both can be appropriate. To assess what a tool returned, select the relevant tool-call span instead. For tool-use judgments, include the applicable tool definitions, available actions and execution evidence as well as the response. [1] [2] A root conversation observation may not expose the system prompt that a separate generation observation contains. [3] [4]

Keep the evaluator's variable names independent of source-specific field names. An illustrative mapping might bind request and answer to dataset columns for an offline batch, but to the request and response fields of a production root span for live traces. A tool-return check would instead map its tool result from the relevant tool span. Before executing, inspect the actual resolved values for representative records: are they present, from the intended run and observation, and complete enough for the question? Missing or wrong values should make a result ungradable, not silently become evidence of failure or success. Mapping makes the evaluation runnable; it does not validate the rubric or the judge. [5] [6]

Evidence modality matters as much as field selection. Text can convey words but cannot itself establish tone, audio timing or interruptions. In one demonstration, a reviewer could operate a music-making app but could not hear its output; functional controls did not establish that the music was good. That limitation concerns the demonstrated setup, not all audio-capable models. Audio-based judging is a possible response, but the advice does not establish its reliability. [7] [8]

For long trajectories, selecting evidence by criterion can make review tractable. A demonstrated verifier ranks screenshots for each rubric item and checks selected images for satisfaction and contradiction. Selection can nevertheless miss the decisive image or a contradiction: inspect what was selected and treat gaps as uncertainty, not proof of absence. Visual overlays can expose apparent fit, but do not by themselves verify every numerical property of a box. [9] [10]

For collecting traces, see Tracing and diagnosing production behavior; for designing criteria and testing whether a judge's judgments are reliable, see Turn task quality into actionable evaluation rubrics and Validate judges against human labels. Supplying inputs is not a substitute for either.

Evaluate faithfulness to supplied evidence

A source-faithfulness question asks whether the answer's claims and decisions follow the evidence supplied, not whether that evidence is true. Give the judge the original retrieved material as well as intermediate research notes when needed; compare numerical claims and their context, not just fluent wording. Inspect whether tool results were empty or unusable and whether the answer discloses such failures. A tool call that completed is not proof that its output supports the answer. [11] [12]

In one financial workshop, a correctness judge relying on its own knowledge marked all thirteen reports incorrect when it treated current events as unknowable future facts. A faithfulness judge given research-turn context classified seven as unfaithful and six as faithful. These were judge outputs in a particular demonstration, not validated financial facts or proof that correctness judges generally fail. A faithful report can faithfully repeat a false or stale source. [13]

Also preserve the sequence of a conversation. A clinical-note example discussed more than one plan but recorded the option the participants had rejected rather than the final decision. The rejected words really appeared in the source, yet matching them was not faithful to the choice. This is a case example, not a measured prevalence of such errors. [14]

Verify sources and critic objections

Before relying on a citation, inspect the retrievable source for existence, relevance, support and sufficient currency for the claim. Distinguish measured observations from source-checked statements, inferences and assumptions; verify or explicitly qualify the latter. [15] Check a critic's objection against the underlying evidence before changing the artifact: an adversarial reviewer can also be wrong. [16]

A speaker recounted a search example in which an answer and its verifier agreed with a stale seed, while later search contradicted it. The ownership details were tentative; the lesson is shared-source failure, not a verified corporate-history claim. Asking the same model to confirm its own citation likewise does not create independent evidence. Even a fresh source can be incomplete or wrong, so source checking increases the basis for confidence rather than guaranteeing truth. [17] [18]

Supply policy, case context and qualified behavior signals

Give the judge the applicable policy and the environment's available tools and contracts. A helpful-sounding refund response is not compliant if it violates a non-negotiable return rule. Make the task specification explicit: if a noninteractive agent must return a report inline rather than write a file, tell it so and judge against that actual environment. A proposal to give judge and producer comparable retrieval access can reduce an information mismatch, but shared access is not independent verification and can reproduce the same retrieval error. [19] [20] [2]

The significance of an omission can depend on the case. A speaker contrasts two travel-history omissions in otherwise similar clinical scenarios, one described as irrelevant and the other as potentially decisive. The claim is contextual, not a universal medical rule. One proposed design retrieves relevant expert corrections, prior judgments and guidance for each case while keeping general instructions stable. It may make evolving standards inspectable, but retrieval relevance, conflicts and propagation of mistaken corrections remain unresolved; it is not proof that fixed rubrics or learned weights always fail. [21] [22]

For personalized tasks, profiles and session behavior can help interpret an ambiguous request, but listening history or reformulation is a proxy, not the user's explicit intent or satisfaction. Shared-device use and other context can distort it. Judge with the available context while preserving those uncertainties; check the reference and proxy separately where the decision warrants it. [23] [24] See Agreement, truth and the limits of evaluator proxies.
